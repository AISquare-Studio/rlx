## 0. The design in one screen

- **One list, owned by Python.** Two tables in the rlx store, `pending` (the items) and `pending_log` (every change, in order). Only Python writes them.
- **rlxd serves it and never touches the table.** It forwards every `pending.*` request to the brain (handoff §1.6), with the caller's verified role attached. It publishes the brain's change events on a new topic, `pending`.
- **Every change reaches the stream.** A change and its `pending_log` row commit in one transaction, whichever process makes it: the brain, the CLI, Remote or a hook. The brain tails the log and hands each row to rlxd in order.
- **The owner rule is data, checked by the store.** Every item carries two computed fields, `owner_only` and `assumable`. The store checks them on every manager action, whoever calls and through whichever surface. The asker can raise `owner_only`, never lower it, and the protected kinds force it.
- **Answering is delivering.** An item leaves the open list only once its answer has reached the asker, or may have (`delivery.state: "maybe"`). It never leaves on a failed delivery. Each source has one deliverer:
  - a board question gets a board note to the asker (Python);
  - a pane dialog gets keys typed into the pane (Python: tmux today, rlxd's PTY host after handoff §1.8);
  - a gate approval becomes `run.decide` (rlxd);
  - a run's question becomes `run.resume {reply}` (rlxd).
- **First answer wins, on every device.** A per-item claim makes exactly one answer deliver. Every later answer gets `already_answered`, and every device sees the winner in `pending.answered`.
- **`needs_you` links to pending.** A need that has an answer is a pending item. A need that is only a state (an agent crashed, the manager is down) stays a `needs_you` signal. When both exist, `needs_you.raised` carries the item's `pending_id`, so a client shows one card. There is one list, `pending.list`.
- **The off switch** is one home setting, `[pending] enabled`, on by default. When it is off, every `pending.*` call but `pending.settings` returns `pending_off`, the sources stop adding items, and every surface hides.
- **The unread dot** (§12) means "not glanced at yet". The home keeps one `last_seen_seq` and one mute flag, shared by every device.
  - An item added while no surface has the Pending section open sets the dot, on the TUI sidebar and in rlx.app's navigation.
  - When no TUI and no app is live, the tray icon shows it instead.
  - Opening the section anywhere clears it everywhere.
  - Surfaces report an open section with `pending.view {open}`. The brain computes the state and emits `pending.dot_changed`.
- **Open questions are listed in §15.** Every pick on the owner rule or on security is marked **Proposed** and listed there, for the owner or the hub to confirm. None is final.

## 1. Words used here

- **The person:** the human who owns the rlx home.
- **The manager:** the fleet manager agent of the item's project (its board session with role `manager`), or the manager of a parent board the item was routed to.
- **An agent:** any other fleet agent, or any process running inside an agent's pane.
- **An item:** one thing waiting on the person.
- **A source:** what added an item (§4).
- **Delivery:** handing an answer back to the asker (§9).
- **A surface:** where the person sees the list. The brief's three are the Claude Code mod, the TUI and rlx.app. Remote and the CLI also read it.
- **The Pending section:** the list's own place in the TUI and in rlx.app, behind their sidebar or navigation entry. The Claude Code panel is not the section (§12.1).
- **A view:** one surface showing the Pending section right now (§12.2).
- **`pending_seq`:** the durable, per-home sequence number of `pending_log`. It is not rlxd's bus `seq`.

## 2. Where it lives, and who does what

```text
   sources (Python)              rlx store (SQLite, Python only)          rlxd
   board writes ──────────┐      ┌──────────────────────────────┐
   watch-cycle scan ──────┼────▶ │ pending      (items)         │      ┌─────────────────┐
   rlx pending (CLI) ─────┤      │ pending_log  (every change)  │ ◀──▶ │ brain (stdio)   │◀──▶ socket clients
   Remote (needs/answer) ─┘      └──────────────────────────────┘      │  serves pending.*│    app, tui, remote, cli
                                        ▲          tails the log ──────▶│  emits events   │──▶ topic "pending"
   gate and run sources (rlxd) ─────────┘ (as notifications to the brain)└─────────────────┘
```

- **The store** (`core/store.py`) holds `pending` and `pending_log`, added in one migration after the 0.10.2 sync. Their columns are in §3.3.
- **The pending service** (`services/pending.py`) is the only code that writes those tables. It does classification, add, answer, assume, dismiss, confirm and delivery. The CLI, the brain, the sources and Remote all call it.
- **The sources** are Python:
  - board sources add their item in the same store transaction as the board event, so a question is on the list the moment it is on the board;
  - pane dialogs, and closing items whose source has resolved, run in the watch cycle. That cycle runs in the brain while rlxd runs, and in `rlx watch` otherwise.
  - The gate and run sources are rlxd's. rlxd hands them to the brain as notifications (§2.1).
- **The brain** (`rlx brain --stdio`, handoff §1.6) serves `pending.*` for rlxd. It tails `pending_log` and hands rlxd one event per row.
- **rlxd** does four things here:
  - it authenticates the caller's role (§8);
  - it forwards requests to the brain;
  - it publishes events;
  - it owns the gate and run deliveries.

  It never opens the SQLite file.
- **The CLI, `rlx pending`,** calls the service in its own process, so it works with rlxd down. Its writes reach rlxd's stream through `pending_log`. When rlxd is up, the CLI also sends a best-effort `pending.poke` notification over the socket, so the brain publishes at once rather than on its next tail.

### 2.1 How rlxd reads and writes the list: the brain calls

rlxd and the brain already speak JSON lines over the brain's stdio (handoff §1.6). Pending adds these frames:

```json
{"id": "r41", "method": "pending.answer",
 "params": {"id": "pnd_01m8b2c3d4e5f6g7h8j9k0m1n2", "answer": [{"labels": ["rc/0.10.3"]}], "expected_version": 1},
 "caller": {"conn": "c12", "role": "app", "client": "rlxapp", "client_version": "0.1.0",
            "verified": "gate", "device": {"name": "anmol-mbp", "route": "local"}, "peer_agent": null}}
{"id": "r41", "ok": true, "data": {"item": {}}}
{"notify": "pending.event", "pending_seq": 418, "type": "pending.answered", "data": {"item": {}}}
```

- **Requests (rlxd to the brain).**
  - rlxd forwards each socket `pending.*` request as it came, adding `caller`. rlxd fills `caller` from the connection, never from the params:
    - `verified` is `gate` for an app-role connection that passed handoff §5.1's checks, and `token` for every other role;
    - `device` names the paired gate device (task #10) for the app, and is `null` otherwise. For Remote, the Remote server's own device field is passed in the params (§8);
    - `peer_agent` is set once handoff §1.8 has moved the fleet onto rlxd's PTY host: rlxd then checks whether the socket peer's process descends from a fleet agent's PTY child (§8.2).
  - rlxd returns the brain's envelope under the socket request's `id`.
- **The wait.** rlxd waits up to 30 s for the brain, because a pane delivery types into a pane. After that it answers `brain_unavailable`. That error is retryable, and the item is unchanged unless a `pending.*` event later says otherwise.
- **Events (the brain to rlxd).** One `pending.event` notification per `pending_log` row, in `pending_seq` order. rlxd publishes each one on topic `pending` with its own bus `seq` and `time` (handoff §7.3), and drops any `pending_seq` it has already published.
  - **After a restart.** rlxd keeps the last `pending_seq` it published in `rlxd.db`. When the brain (re)starts, rlxd sends `pending.resume_from {pending_seq}`, and the brain replays the log rows after it. No change is lost to a restart of either.
- **The tail.** The brain reads new `pending_log` rows every 1 s. It also reads them at once after its own writes, and on a `pending.poke`. A write by any process therefore reaches the stream within about a second.
- **The brain asks rlxd to deliver** what rlxd owns (§9). Each of these is a brain-to-rlxd request:
  - `gate.decide_for {conn, run_id, call_id, decision, reason}`. rlxd runs `run.decide` on behalf of connection `conn`, and it checks again, itself, that `conn` is an app-role connection. So handoff §5.1's "only the app decides" stays enforced in rlxd, not only in the brain;
  - `run.resume_for {conn, run_id, reply}`;
  - `pty.write`, after handoff §1.8, for pane dialogs.
- **Sources (rlxd to the brain).** These are notifications:
  - `source.gate_waiting {pending_id, run_id, call_id, attempt, kind, tool, input, input_sha256, deadline_at, space}`;
  - `source.gate_decided {run_id, call_id, decision, by, device?}`;
  - `source.run_needs_you {pending_id, run_id, attempt, reason, question?, space}`;
  - `source.run_resumed {run_id, attempt}`;
  - `source.runs_erased {run_ids}`;
  - on every brain start, `source.snapshot {gate_waiting: [...], runs_needing_you: [...]}`. The brain closes any open rlxd-sourced item that is missing from it.

  rlxd mints `pending_id` for its own sources. It can then put the same id in `needs_you.raised` at once (§10), before the brain has written the row.
- **For the unread dot (rlxd to the brain, §12.4),** two more notifications:
  - `view.changed {conn, open, device}` when a connection's `pending.view` changes, or when a connection with an open view drops (`open: false`);
  - `clients.changed {app, tui, remote, cli}` when `status.clients` changes.
- **The brain is down.** `pending.*` calls get `brain_unavailable`. The gate, the runner and `needs_you` keep working: none of them waits on pending.

### 3.2 Every field

The fields the brief names are marked **(brief)**. Every other field says why the API needs it. Times are RFC 3339 UTC with milliseconds, as the bus envelope's `time` is (handoff §7.3).

**Identity and concurrency**
- `id` (string): `pnd_` and a 26-character lowercase ULID. It is stable for the item's whole life. **(brief)**
- `version` (integer ≥ 1): 1 at add, plus 1 on every change. It is what `expected_version` compares against (optimistic concurrency), and clients keep the copy with the highest `version` of each `id` (§7.2). **Added.**
- `added_seq` (integer): the `pending_seq` of the item's `pending.added` row. It never changes. **Added:** the unread dot compares it with the home's `last_seen_seq` (§12.2). It is the brief's "item seq".
- `changed_seq` (integer): the `pending_seq` of the item's last change. It is the durable cursor that `pending.list {since}` filters on. **Added.**

**Who asks, and where**
- `project` (`{id, name}` or `null`) **(brief)**. It is `null` for items with no project: rlx.app runs live in spaces (handoff §2.5).
- `space` (string or `null`): the run's space, for gate and run items. **Added:** an app run has a space and no project.
- `asker` (object) **(brief: "agent label or session")**:
  - `type`: `agent`, `session` (a board session no fleet row holds) or `run`;
  - `label`: what the surfaces show;
  - `role`, `session_id`, `agent_id` and `run_id`: each a string or `null`.

  Delivery uses them to address the answer, and the manager check uses them to tell an asker's own item apart.

**What is asked**
- `kind` (string enum, §5.1): the class of decision. It drives the owner rule. **(brief)**
- `text` (string, at most 8,192 characters): one plain headline. It is what a list row shows. **(brief)**
- `questions` (array, 1 to 8 entries): what the answer flow asks. One entry for every source except a multi-question AskUserQuestion. For one question, `questions[0].text` equals `text`. **Added:** an AskUserQuestion holds up to 4 questions, answered together, so one dialog is one item with several questions. Each question has:
  - `header` (string or `null`): the AskUserQuestion chip, at most 12 characters;
  - `text` (string);
  - `multi_select` (boolean);
  - `free_text` (boolean): whether a typed answer can be delivered to this source. It is true for every source except first-run and trust screens (§4). The brief's "free text always available" holds wherever delivery can carry text;
  - `suggested` (array, 0 to 16 entries) **(brief: "suggested answers, label plus description, the AskUserQuestion shape")**. Each entry is `{label, description, recommended}`, where `label` is a string of at most 200 characters and `description` a string or `null`. `recommended` is true on at most one entry of a single-select question. It marks the suggested default that `pending.assume` takes. An AskUserQuestion option whose label ends in "(Recommended)" reads as `recommended: true`.
- `detail` (object or `null`, at most 16 KiB): what the person must read before answering, by source: the full command of a permission prompt, a plan, or a gate call's `{tool, input, input_sha256, deadline_at}`. It is never pushed to a lock screen (§8.4). **Added:** it is the same split Remote's `NeedsItem` makes between a card's line and what an unlocked page shows.

**The owner rule (§5)**
- `owner_only` (boolean) **(brief)**. Computed at add, from the asker's flag and the kind. It can only be raised, never lowered.
- `owner_only_why` (array of `asker`, `protected_kind`, `authorization`, `protected_words`): why the item is owner-only. **Added:** a surface can say why an item waits for the person, and a test can assert the reason.
- `assumable` (boolean): whether `pending.assume` can ever take it (§5.3). **Added:** a client can show "waits for you" and the manager need not try.
- `answer_roles` (array of `hello` roles): who may answer the item (§8.3). Gate items and the app-only run items list only `app`. **Added:** a client then needs no knowledge of source types to know whether it may answer.

**Where it came from**
- `source` (object): `{type, key, …}`. Its fields by type are in §4. **Added (the contract's "source ref"):**
  - `key` is unique across all items, open or closed, so a scan that sees the same need again adds nothing (§4.1);
  - the rest is what delivery and closing at the source need.

**Its life**
- `created` (time) **(brief)**.
- `assume_after` (time) **(brief)**: `created` plus `[pending] assume_after_hours` (default 24), unless the asker gave its own. It is set on every item. An owner-only item past it stays open (§5).
- `status`: `open`, `answered`, `assumed` or `dismissed` **(brief)**.
- `answer` (array or `null`) **(brief)**: one entry per question, in order, each `{labels: [string], text: string or null}`. `labels` are suggested labels; `text` is free text. A question needs at least one of the two.
- `answer_text` (string or `null`): one line in words, built by the store, for board notes and list rows. **Added.**
- `answered_by` (enum or `null`) **(brief: person or manager-assumed; extended)**:
  - `person`: the person answered through a surface;
  - `manager-assumed`: the manager took the suggested default after `assume_after` (`status: "assumed"`);
  - `manager`: **added, Proposed (OQ-3).** The manager answered with an answer it found, which the brief's "answers items it has found answers to" asks for. It is kept apart from `person`, so the Assumed section can show it;
  - `elsewhere`: **added.** The source shows the need resolved without pending: the person typed into the pane, replied on the board, decided in rlx.app's own gate dialog, or the task left `blocked`. Without it, the list would keep a question the person had already answered.
- `answered_at` (time or `null`) **(brief)**.
- `answered_device` (object or `null`): `{surface, name, route, client}`, where `surface` is one of `app`, `tui`, `remote`, `cli`, `claude_code` and `manager`. **Added (the contract's "device"):** with several devices, every device shows who answered, from where, as the per-device gate does for decisions (task #10). For the app, `name` is the paired gate device's name and `route` is `local` or `ssh`.
- `delivery` (object or `null`): `{state, at, via, ref, detail}`, where:
  - `state` is `delivered`, `maybe` or `not_needed`;
  - `via` is `board`, `pane`, `gate`, `run` or `fleet`;
  - `ref` is what was written: `{board, event_seq}` of a board note, `{run_id, call_id, decision}`, or `{agent_id, keys}`.

  **Added:** the brief says answering delivers to the asker. This field records that it did, or that it may have (`maybe`: tmux timed out mid-write, §9.2).
- `needs_confirm` (boolean): true while `answered_by` is `manager` or `manager-assumed` and the person has neither confirmed nor changed the answer. **Added:** it is the brief's "Assumed: confirm or change" section, as one filter.
- `confirmed_at` (time or `null`): when the person confirmed an assumed or manager answer. **Added.**
- `dismissed_by` (`person`, `asker`, `source` or `null`). **Added:** a dismissal by the person reads differently from an expired gate call.
- `closed_reason` (`resolved_at_source`, `asker_gone`, `expired`, `erased` or `null`): set when the source closed the item (`answered_by: "elsewhere"` or `dismissed_by: "source"`). **Added.**

Content is immutable. `kind`, `text`, `questions`, `detail` and `source` never change after add. A dialog whose question changes is a new prompt, with a new `tool_use_id`, so it becomes a new item, and the old one closes at its source. So no client ever answers text other than the text it read.

### 3.3 The store's tables (for task #18)

- **`pending`** has one row per item: every field of §3.2 as a column, or JSON for the objects. It also has:
  - `source_key TEXT NOT NULL UNIQUE`;
  - `claim_token TEXT` and `claim_expires_at TEXT`, the answer claim (§6.3).

  Indexes: `(status, created)`, `(project_id, status)`, `(changed_seq)` and `(added_seq)`.
- **`pending_log`** has one row per change:
  - `seq INTEGER PRIMARY KEY AUTOINCREMENT`, which is the `pending_seq`;
  - `item_id`, `type` (the event type of §7), `version` and `at`;
  - `actor`: `person`, `manager`, `agent`, `source` or `asker`;
  - `device` (JSON) and `data` (JSON: the event's extras, such as `previous`).

  It is the outbox of §2.1 and the history that `pending.get` returns. A move of the unread dot's marker is a row too (`type: "seen"`, no `item_id`), so any process's move reaches the brain (§12.4).
- **`pending_meta`** is a small key/value table for home-wide state. It holds `last_seen_seq` (§12.2), and is updated in the same transaction as its `seen` row.
- **Retention.** A closed item and its log rows are kept for 30 days after closing, as run event logs are (handoff §1.7), then pruned. `seen` rows are pruned after 30 days. An open item is never pruned: "Those wait, however long it takes."

## 4. Sources

### 4.1 The rule every source follows

- **One need, one item, ever.** Each source derives a `source.key` from what the need is about: a board event's seq, a `tool_use_id`, a `call_id`, a run attempt. An add whose key exists is a no-op. So a scan every cycle adds nothing new, and a dismissed item stays dismissed while its source still shows it. A new prompt is a new key, and so a new item.
- **Closing at the source.** Each source also says when its need has gone. The watch cycle (and rlxd's notifications, for rlxd's sources) closes such items with `answered_by: "elsewhere"` or `dismissed_by: "source"`, and sets `closed_reason`.
- **The off switch.** While `[pending] enabled` is false, no source adds (§11).

- **Not sources.** The scan's other kinds stay `needs_you` signals with no item (§10): `crashed`, `lost`, `manager_down`, `fleet_down`, `failed`, `interrupted`, and `limited` while the hand-over is moving the agent. They are states, not questions.
- **What the asker can give a board question.** Task #18 names the flags, but their meaning is fixed here, because the owner rule depends on it:
  - owner-only, which raises `owner_only`;
  - a pending kind (§5.1);
  - suggested answers, as `label` and `description`;
  - which suggestion is recommended;
  - its own `assume_after`.
- **The manager adding by hand.** The manager can put an item on the list itself, with `rlx pending add` and the same fields, as a `board_question` written through the board. So everything goes through one path.

## 5. Classification and the owner rule

The owner's rule: assumed answers only for safe, reversible items (preferences, clarifications). The manager never assumes, or answers for the person:
- a merge to main, a release (bump, tag, publish), or spending;
- deleting anything;
- sending a message or email on the person's behalf;
- anything its asker marked owner-only.

Those wait, however long it takes. This section makes that rule a check in the store, run on every manager action, whoever calls.

### 5.1 `kind`

- **The owner's protected kinds:** `merge_main`, `release`, `spend`, `delete` and `send_as_person`. Each is one item of the owner's list.
- **Authorizations, Proposed (OQ-1):** `permission`, `plan`, `first_run`, `gate_call` and `connector_auth`. Answering one lets an agent act, and the classifier cannot bound what that act is: a permission prompt may be `rm -rf` or `gh pr merge`, and a gate call may be a Slack send. So each could be any of the owner's five.
- **Safe classes:** `preference` and `clarification`, the owner's own words.
- **Unclassified:** `question` (the default for a board question and an AskUserQuestion), `blocked` and `handover`.

An asker sets `kind` only on a board question. Every other source sets it by the table in §4.2. A future source must add its kind to one of these four groups, and an unknown kind is treated as an authorization.

### 5.2 `owner_only`

`owner_only` is true when any of these holds. Each adds its tag to `owner_only_why`:
- **`asker`:** the asker marked the item owner-only;
- **`protected_kind`:** `kind` is one of the owner's protected kinds;
- **`authorization`:** `kind` is an authorization (Proposed, OQ-1);
- **`protected_words`** (Proposed, OQ-4): for the unclassified kinds only, the item's text or any suggestion names a protected act: merge (to main), release, tag, publish, a version bump, pay, purchase, buy, spend, credits, delete, remove, drop, `rm`, send, email, post or message. The screen can only raise `owner_only`, never lower it. A false positive makes an item wait for the person, which is the safe direction.

Nothing can clear `owner_only`: not the asker, the manager, the person or a later scan. An asker can mark a `preference` owner-only, but it cannot mark a `merge_main` as not owner-only.

### 5.3 `assumable`

`assumable` is true only when all of these hold:
- `owner_only` is false;
- `kind` is `preference` or `clarification`. This is Proposed (OQ-2): the owner's rule names only those. An unclassified `question`, a `blocked` task and a `handover` are never assumed, and an asker that wants its question assumable classifies it;
- every question has a recommended suggestion. For a multi-select question, the recommended entries make the default set.

### 5.4 The checks, in the API

| Call | Refused with | When |
|---|---|---|
| `pending.assume` | `owner_only` | `owner_only` is true, for any reason. `detail.why` is `owner_only_why` |
| `pending.assume` | `not_assumable` | `assumable` is false for another reason. `detail.why` is `kind` or `no_default` |
| `pending.assume` | `too_early` | now is before `assume_after`. `detail.assume_after` says when |
| `pending.assume` | `not_manager` | the caller is not the manager of the item's project (§8) |
| `pending.answer` from the manager (Proposed, OQ-3) | `owner_only` | `owner_only` is true |
| `pending.answer` from an agent that isn't the manager | `not_person` | always |
| `pending.dismiss` from the manager or an agent | `not_person` | always, unless the caller is the item's own asker withdrawing it (`dismissed_by: "asker"`) |
| `pending.settings` (a write), from the manager or an agent | `not_person` | always: an agent must not be able to hide the list (§11) |

- **Who calls doesn't matter.** These checks run in the pending service, on the row, inside the claim of §6.3, for every caller: the CLI, the brain, Remote. They don't rest on rlxd's routing or on what a surface chooses to show.
- **Every refusal is logged.** It writes a `pending_log` row (`type: "refused"`), which `pending.get` shows. It is not an event.
- **Each check is a test.** Task #18's tests drive every row of this table, and a test that can't fail is a bug (handoff, "How to read the checks").

## 6. Methods

Every method is a socket request (`{"id", "method", "params"}`, handoff §7.2). Its result is the v1 envelope. The CLI form is in §6.8. The unread dot's three methods, `pending.view`, `pending.seen` and `pending.dot`, are in §12.8.

Errors every method can return:
- `pending_off`: the switch is off (§11). Every method but `pending.settings` returns it;
- `brain_unavailable`: retryable;
- `invalid_params`: `detail` names the field;
- `not_found`: no item has that `id`.

### 6.1 `pending.list {status?, project?, since?, needs_confirm?, limit?}`

- **Params:**
  - `status`: a status, or an array of them. The default is `["open"]`, or every status when `since` is given;
  - `project`: a project id, or `null` for items with no project. Left out, it means every project;
  - `since`: a `pending_seq`. It returns the items with `changed_seq > since`, ordered by `changed_seq`. A client that missed events uses it to re-read only what changed;
  - `needs_confirm: true`: only the "Assumed: confirm or change" section;
  - `limit`: default 200, at most 1,000.
- **Result:** `{enabled, items, counts: {open, open_owner_only, needs_confirm}, pending_seq, more}`.
  - `counts` is over the filter's project, whatever the limit. It is the badge, and the panel's "N more";
  - `pending_seq` is the log head the result reflects;
  - `more` says the limit cut the result. Continue from the last item's `changed_seq`.
- **Order.** Without `since`, the oldest `created` comes first, because everything on the list is waiting and the oldest has waited longest. Surfaces may sort as they like.
- **Errors:** the common ones only.

### 6.2 `pending.get {id}`

- **Result:** `{item, history}`. `history` is `[{pending_seq, at, type, version, actor, device}]`, the item's `pending_log` rows, refusals included.
- **Errors:** `not_found`.

### 6.3 `pending.answer {id, answer, expected_version?, as?, device?}`

- **Params:**
  - `answer`: one `{labels, text}` per question, in order (§3.2);
  - `expected_version`: if given and not the item's `version`, the call is refused with `version_conflict` and the current item in `detail.current`. It protects an answer to a card read before the item changed: for example, an assumed item that another device has already changed;
  - `as`: the caller's board session, for a manager answer (§8.2);
  - `device`: for Remote and the Claude Code mod only (§8). rlxd ignores it from every other role.
- **What it does, in order:**
  1. **Check:** the caller, `answer_roles`, the status and `expected_version`. Then, for a manager, the owner rule (§5.4). Then that `answer` fits the item.
  2. **Claim:** a conditional update sets `claim_token`, only while the item has no live claim (30 s lease). A concurrent answer gets `busy`, which is retryable. So two devices can never both type into one pane, and a crashed answerer's claim lapses.
  3. **Deliver,** by the source's deliverer (§9).
  4. **Commit:** on `delivered` or `maybe`, the update sets `status`, `answer`, `answer_text`, `answered_by`, `answered_at`, `answered_device` and `delivery`, clears the claim, adds 1 to `version` and writes the log row. All of that is one transaction.
  5. **Release:** on a failed delivery, the claim is released and nothing else changes.
- **An item in "Assumed: confirm or change".** On an item whose `needs_confirm` is true, a person's answer changes the assumed answer:
  - the status becomes `answered`, with `answered_by: "person"`;
  - the new answer is delivered to the asker. A pane dialog that has gone gets it as a board note to its label instead;
  - the manager gets a board note naming the old answer and the new one ("redo what depended on it"), addressed `--to manager`, which wakes it (`team._addressed_to_manager`);
  - the event is `pending.changed` (§7).
- **Result:** `{item}`.
- **Errors:**
  - `already_answered`: the item is not open and is not a `needs_confirm` item. `detail.item` shows who won and from which device. This is `already_decided`'s counterpart (handoff §5.1);
  - `version_conflict`;
  - `busy`;
  - `not_person`;
  - `not_gate`: a gate item, or an app-only run item, answered from a role other than `app`. This keeps handoff §5.1's rule;
  - `owner_only`;
  - `bad_answer`. `detail.why` is one of:
    - `label`: a label that is not a suggestion;
    - `count`: the wrong number of answers;
    - `multi`: several labels on a single-select question;
    - `text`: text where `free_text` is false;
    - `empty`;
    - `not_deliverable`: the agent's keys can't express it, §9.2;
  - `stale`: the pane no longer shows that dialog. Nothing is typed, the item closes at its source, and `detail.current` lists what the pane shows now;
  - `too_late`: the gate call's deadline passed. The item closes `expired`;
  - `delivery_failed`: `detail` is `{via, code, message, retry}`. The item is still open.

### 6.4 `pending.dismiss {id, expected_version?, reason?}`

- **Who:** the person; or the item's own asker, withdrawing its question. The asker is recognised by `as` naming the asker's session (§8.2).
- **What:** `status: "dismissed"`, `dismissed_by: "person"` or `"asker"`. Nothing is delivered, and the asker is not told: a dismissal says "not now", not "no". `reason` (at most 500 characters) goes into the log.
- **Result:** `{item}`.
- **Errors:** `not_open`, `version_conflict`, `busy`, `not_person`.

### 6.5 `pending.assume {id, expected_version?, as}`

- **Who:** the manager only (§8.2).
- **What:** it takes each question's recommended suggestion, and delivers it as an answer would, but marked "assumed after N h; the person may change it". It commits `status: "assumed"`, `answered_by: "manager-assumed"` and `needs_confirm: true`. It takes no answer of its own: an assumption is always the suggested default.
- **Result:** `{item}`.
- **Errors:** `not_manager`, `not_open`, `version_conflict`, `busy`, `owner_only`, `not_assumable`, `too_early`, `delivery_failed`.

### 6.6 `pending.confirm {id, expected_version?}`

**Added:** the brief's "confirm or change" needs a confirm.

- **Who:** the person.
- **What:** it sets `confirmed_at` and `needs_confirm: false`. Nothing is delivered.
- **Result:** `{item}`.
- **Errors:** `not_needed` (the item is not `needs_confirm`), `version_conflict`, `not_person`.

### 6.7 `pending.settings {enabled?, assume_after_hours?, dot_muted?}`

- **Read:** with no params. It returns `{enabled, assume_after_hours, pane_dialog_after_s, dot_muted}`. `dot_muted` is the unread dot's mute (§12.7).
- **Write:** with params, from the person only (`not_person` otherwise). The value is written to `[pending]` in the home's `config.toml` through the CLI's config writer, so config writes stay in the CLI. Then `pending.settings_changed` is emitted.
- **The bounds:** `assume_after_hours` is an integer from 1 to 720. A new value applies to items added after it. An item's `assume_after` never moves.
- **Errors:** `not_person`, `invalid_params`.

### 6.8 The CLI

`rlx pending` maps one-to-one onto these methods, in-process (§2):
- `list` is `pending.list`, and `show <id>` is `pending.get`;
- `answer <id> …` is `pending.answer`;
- `assume <id>` is `pending.assume`. The CLI fills `as` from the agent's own session, as `aisquare` does for `--as`;
- `dismiss <id>` is `pending.dismiss`.

It adds `confirm <id>`, `settings [--on | --off] [--assume-after-hours N] [--mute-dot | --unmute-dot]`, `dot` and `seen` (§12.8).

Output:
- `--json` prints the bare `data`;
- `--json --schema-version 1` prints the v1 envelope (handoff §3.1 A1). It waits for #578, like A1's other commands;
- error codes are the API's.

## 7. Events: topic `pending`

### 7.1 Types and `data`

Every event goes in the handoff §7.3 envelope, with `topic: "pending"`. Every item event's `data` holds `pending_seq` and the whole `item` after the change. Some types add extras, and the two home-wide events (`pending.settings_changed`, `pending.dot_changed`) carry no item:

| Type | When | Extras in `data` |
|---|---|---|
| `pending.added` | a source added an item | none |
| `pending.answered` | an answer was delivered and committed, by the person, the manager or the source (`answered_by: "elsewhere"`) | none |
| `pending.assumed` | `pending.assume` committed | none |
| `pending.dismissed` | the person, the asker or the source dismissed it | none |
| `pending.changed` | the person changed an assumed or manager answer | `previous: {answer, answer_text, answered_by, answered_at}`, `manager_told: {board, event_seq}` |
| `pending.confirmed` | **added:** the person confirmed one. Other devices drop it from their Assumed section | none |
| `pending.settings_changed` | **added:** the switch, the default or the dot's mute changed. Every surface hides or shows at once | `enabled`, `assume_after_hours`, `dot_muted`, `device`. It has no `item` |
| `pending.dot_changed` | **added:** the unread dot's `dot`, `tray` or `muted` changed (§12.8). Every surface and the tray update together | the dot state, `{dot, tray, muted, last_seen_seq, newest_seq, live: {tui, app}}`, plus `device`. It has no `item` |

```json

 "data": {"pending_seq": 433,
          "item": {"id": "pnd_01m8b2c3d4e5f6g7h8j9k0m1n2", "version": 4, "status": "answered", "answered_by": "person"},
          "previous": {"answer": [{"labels": ["rc/0.10.3"], "text": null}], "answer_text": "rc/0.10.3",
                       "answered_by": "manager-assumed", "answered_at": "2026-11-26T16:05:00.000Z"},

```

(The `item` here is cut short for the page. On the wire it is the whole §3.1 object.)

### 7.2 How a client keeps the list

1. Read `status` for the bus `seq`, `s`.
2. Subscribe with `events.subscribe {topics: ["pending", …], since: s}`.
3. Call `pending.list`.
4. Apply each event by upserting `data.item` by `id`, keeping the highest `version`. Ordering between the list and the stream doesn't matter, because `version` settles it.
5. On `daemon.gap` (handoff §7.3), call `pending.list {since: <the highest pending_seq seen>}`.

Without rlxd (the Claude Code mod, or the TUI before handoff §1.9), a client polls `rlx --json pending list --since <pending_seq>` instead.

### 7.3 What events carry

- An event carries the item's full text and `detail` to every subscriber that holds the token. That is what the board already gives the same clients.
- Remote's push to a lock screen never carries them. It uses a fixed reason passed through `needs_push_safe`, as Remote does today (§8.4).

## 8. Callers, roles and auth

### 8.1 What rlxd can prove, and what it can't

- **The app** (`hello {role: "app"}`) is verified. It holds a paired, per-device gate credential (task #10), and, on the local route, passes the peer check (handoff §5.1). Its answers are the person's, attributed to the gate device's name.
- **`tui`, `remote` and `cli`** prove only the shared token. Anything that can read the token already runs as the user (handoff §1.3). A same-user process can claim any of those roles.
- **Remote** authenticates its own devices (password, cookie, pairing). The Remote server passes the answering device in `device`. rlxd can't check that claim, and treats it as the Remote server's word.
- **The consequence.** No caller identity short of the app's is a security boundary against code running as the user. The owner rule therefore does not rest on caller identity. §5's checks run on the item for every caller, so a forged "manager" can't assume an owner-only item.

  What a forged "person" could do is answer one, and that is the security question for the hub (SQ-1). It is not a new capability, though: an agent that would forge the person's answer to "may I merge to main?" can already run the merge itself. The design blocks the honest-but-wrong paths: a manager answering as the person, or a model relaying an answer.

### 8.2 Who the caller is: the actor

The service works out an `actor` for every call:
- **`person`:** a connection with role `app`, `tui` or `remote`; a `cli` caller not detected as an agent; or the Claude Code mod's hook path (below).
- **`manager`:** the caller names its board session in `as`, and that session is live and holds role `manager` on the item's project board, or on a parent board the item was routed to. The CLI fills `as` from the agent's own session, from the same environment `aisquare --as` reads.
- **`agent`:** any other caller detected as running inside a fleet agent. Detection is best-effort, Proposed (SQ-1):
  - the environment holds the fleet's markers (`AISQUARE_FLEET_AGENT`, `AISQUARE_LAUNCH_ID`);
  - or the process descends from a fleet agent's pane process: tmux's `pane_pid` today;
  - or, once handoff §1.8 has landed, rlxd's `peer_agent`: the socket peer descends from an agent's PTY child. That one is the strongest, because rlxd spawned the tree.

  An agent detected this way is never `person`, whatever role it claims: it is `manager` if `as` checks out, and `agent` otherwise. A double fork or a cleared environment can evade detection, and §8.1 is why that is acceptable but flagged.
- **The Claude Code mod's hook path.** The mod never lets the model write an answer. When the panel opens an AskUserQuestion of pending items:
  - the mod's PreToolUse hook on AskUserQuestion records the `tool_use_id`, and the item ids and versions it asks;
  - its PostToolUse hook reads the person's selections from the tool's result (Claude Code's UI produced them), and calls `rlx pending answer` for each item, with `actor: person`, `device.surface: "claude_code"` and `expected_version`.

  The CLI accepts the person actor on that path only for a `tool_use_id` the PreToolUse hook recorded, and once each. A model's own `rlx pending answer` call, in a fleet agent's session, is an agent's (or the manager's) and is refused or limited as §5.4 says.

  **The mod's first probe** must confirm that PostToolUse carries AskUserQuestion's answers in the Claude Code versions rlx supports. If it doesn't, the mod falls back to the model's call, which then counts as that session's actor, not the person's (SQ-3).

### 8.3 Per method

| Method | app | tui, remote, cli as the person | the manager | an agent |
|---|---|---|---|---|
| `pending.list`, `pending.get` | yes | yes | yes | yes |
| `pending.answer`, open item | any item | items whose `answer_roles` include the role. Gate items and app-only run items: `not_gate` | items that aren't `owner_only`, as `answered_by: "manager"` (Proposed, OQ-3); otherwise `owner_only` | `not_person` |
| `pending.answer`, a `needs_confirm` item (a change) | yes | yes | `not_person` | `not_person` |
| `pending.assume` | `not_manager` | `not_manager` | under §5.4 | `not_manager` |
| `pending.dismiss` | yes | yes | its own question only (as the asker); otherwise `not_person` | its own question only; otherwise `not_person` |
| `pending.confirm` | yes | yes | `not_person` | `not_person` |
| `pending.settings`, read | yes | yes | yes | yes |
| `pending.settings`, write (the off switch, the default, the dot's mute) | yes | yes | `not_person` | `not_person` |

- **Any paired device may answer, and the first answer wins.** That covers every app device (local or over SSH, task #10), every Remote device, the TUI and the CLI, each within its row above. The claim (§6.3) makes exactly one delivery happen. Every device sees the winner, and `answered_device` names it.
- **For a gate item,** the claim and `run.decide`'s own first-answer-wins agree: an app device that decided in its own dialog first makes the item `elsewhere`. A `pending.answer` then gets `already_answered`, as `run.decide` gets `already_decided`.

### 8.4 Text that leaves the machine

Remote's push to a phone's lock screen carries only a fixed reason, passed through `remote_needs.needs_push_safe`. It never carries `text`, `questions` or `detail`, which are served only to an unlocked page. That is today's Remote rule, and pending keeps it.

## 9. Delivery, per source

### 9.1 Who delivers what

| Source | Deliverer | What it does | On failure |
|---|---|---|---|
| `board_question` | Python (the pending service) | `fleet.tell` to the asker's label, with the answer and a reference to the question's seq. `tell` types into a waiting asker, and otherwise files the note on the board for the asker's next delta (today's `rlx fleet tell` rule). A person's answer is written with no session (the human's); a manager or assumed answer, as the manager's session, saying so | The board write is in the same transaction as the commit, so either both happen or neither does: `delivery_failed` |
| `task_blocked` | Python | a board note to the task's claimer and to the manager, with `--task`. The task stays blocked: unblocking it is the manager's job, as today | as above |
| `handover_failed` | Python | "Switch to <account>" runs `fleet switch`, Remote's Switch action. "Wait for the reset", or free text, is a board note to the manager | `delivery_failed` with the switch's error, item open |
| `pane_dialog` | Python: tmux today (`fleet.pane_writes`); after handoff §1.8, the brain asks rlxd for `pty.write` | Remote's discipline, reused: under the agent's action lock, re-derive the agent (`needs_agent_now`), check that the dialog is still the item's (`needs_item_current`, `needs_prompt_now`), map the answer to the agent's keys (`AgentTranscript.answer_keys`), and type them | `stale`: closed at source, nothing typed. `not_agent` or `fleet_unavailable`: `delivery_failed`, item open. A tmux write that timed out (`typed == "maybe"`): committed with `delivery.state: "maybe"`, and the surfaces say "may not have reached the pane" |
| `gate_call` | rlxd (`gate.decide_for`, which is `run.decide`) | "Allow" or "Deny", with the free text as `reason`. With no text, the reason is "answered in Pending" | `already_decided`: `already_answered`, item `elsewhere`. `too_late`: closed `expired`. `not_gate`: refused, nothing changes |
| `run_needs_you` | rlxd (`run.resume_for`, which is `run.resume {reply}`) | the answer's text becomes the reply | `run_alive`: someone resumed first, so `already_answered`, item `elsewhere`. `no_session`: `delivery_failed` with `retry: false` |

### 9.2 Pane answers in detail

- **A suggestion** is the agent's key for that option, by index, never by label text.
- **A multi-select question** is the toggle keys, then submit.
- **Free text** is the dialog's type-your-own entry, the text, then Enter. On a permission prompt, free text is "No, and tell Claude what to do differently", then the text.
- **A multi-question AskUserQuestion** answers its tabs in order, then submits once.
- **What the keys can't express** is refused with `bad_answer` and `detail.why: "not_deliverable"`, before anything is typed. Each question's `free_text` and `multi_select` already say what the source can take, so a well-behaved surface never sends it.
- **Text checks.** The text passes Remote's `check_remote_text` and its length bound, `SEND_KEYS_TEXT_MAX`.

### 9.3 Assumed answers are delivered the same way

`pending.assume` delivers through the same deliverer as an answer would. Under OQ-2, only board-sourced `preference` and `clarification` items can be assumed, so in 0.10.3 an assumption always arrives as a board note. A later change delivers again (§6.3).

## 10. `needs_you` and pending: linked, one list

**The decision.** Pending links to `needs_you`: it neither supersedes nor wraps it.
- **A need that has an answer is a pending item, and `pending.list` is the one list of them.**
- **A need that is only a state is a `needs_you` signal,** and is never on the list.
- **When both exist they are the same need:** `needs_you.raised` and `needs_you.cleared` carry an optional `pending_id`, an additive field (§13). A client shows that need once, as the pending item.

| Need | `needs_you` (handoff §7.3) | Pending item |
|---|---|---|
| a run's question (`run.needs_you {reason: "question"}`) | `needs_you.raised {source: "run", reason: "question", pending_id}` | yes, `run_needs_you` |
| a run the app stopped (`run.needs_you {reason: "denied"}`) | `needs_you.raised {source: "run", reason: "denied", pending_id}` | yes, app only |
| a connector needing auth (handoff §5.5) | `needs_you.raised {source: "run", reason: "auth", pending_id}` | yes, app only |
| a dialog in a fleet agent's pane (after handoff §1.8) | `needs_you.raised {source: "fleet", reason: <dialog>, pending_id}`, raised by the brain from the same scan | yes, `pane_dialog` |
| a failed hand-over | `needs_you.raised {source: "fleet", reason: "handover_failed", pending_id}` | yes, `handover_failed` |
| a board question to the person, a task blocked on the person | none: the `board` topic carries the event | yes |
| crashed, lost, manager down, fleet down, a failed turn, interrupted, limited while handing over | `needs_you.raised {source: "fleet", reason}`, with no `pending_id` | no |

- **Why link, and not supersede or wrap.**
  - `needs_you` is in the 0.10.3 contract already. Its checks (handoff §7.3, "needs_you, from runs") and rlxapp's traceability row both rest on it, and its health signals have no answer, so they have no place on a list of questions.
  - Superseding would drop those signals.
  - Wrapping would make the topic a second copy of the list.
  - Linking keeps both contracts as they are, and adds one field. rlxd mints the id for its own sources (§2.1), so the link is present on the first `needs_you.raised`.
- **Remote, the M7 strip and B2's needs-you lane** (0.10.2) follow the same rule once task #18 lands:
  - their decision cards are pending items;
  - their health cards stay;
  - Remote's `POST api/needs/answer` on a card that has a pending item becomes `pending.answer`, so the item closes and every device sees it. Until then, a Remote answer closes the item at its source on the next scan (`elsewhere`).
  - The pane source is Remote's own classifier, so the two can't disagree about what is up.

## 11. The off switch

- **One value per home:** `[pending] enabled` in the home's `config.toml`, default `true`. It is read by every surface and by the Python sources. It is not rlx.app's per-device notification switch (multi-device brief §4), which stays device-local.
- **Off means:**
  - the sources add nothing;
  - every `pending.*` call but `pending.settings` returns `pending_off`, with a hint naming the way back on;
  - every surface hides. The Claude Code mod drops its panel, the TUI drops its panel (M7's strip shows only health), and rlx.app drops its badge, section and cards. Each acts on `pending.settings_changed`, or on a `pending_off` it gets;
  - the manager is told the list is off. Its briefing then asks it to carry questions in its replies, as it did before this feature.
- **Off never touches** the gate, the runner, `needs_you` or the board. A gate call still reaches the app as `run.tool_call`.
- **Items are kept while it is off,** frozen. When it is turned back on, the next watch cycle closes the items whose source has resolved, and adds what is waiting now.
- **Only the person can turn it off or on** (§8.3). An agent must not be able to hide the list. This is Proposed (SQ-6).
- **Off also means no dot.** With the list off, `dot` and `tray` are false (§12).

## 12. The unread dot

The owner's addition to the brief, "The unread dot": the dot means "not glanced at yet", not "not addressed". It clears when the person opens the Pending section, whether or not anything has been answered.

### 12.1 Where it shows

- **Shows:**
  - on the Pending entry of the TUI sidebar;
  - on the Pending entry of rlx.app's navigation;
  - on rlx.app's OS badge (the macOS dock, the Windows taskbar), as a dot, never a count (§12.6);
  - on the tray or menu-bar icon, only while neither a TUI nor the app is live (§12.5).
- **Never shows on the Claude Code panel.** The panel always lists the items, muted or not, and has no dot. Seeing the panel doesn't count as opening the section either (DQ-2): the panel is always on screen beside a chat, so counting it would stop the dot from ever appearing while a Claude Code session runs.
- **One state per home.** Every surface shows the same dot, because they all read one state, computed by one function (§12.4).

### 12.2 What is stored, and what is only live

- **`added_seq`, on every item** (a new field in §3.2): the `pending_seq` of the item's `pending.added` row. It is what "the newest item seq" means.
- **`last_seen_seq`, one per home:** the newest `added_seq` the person has seen. It is stored with the list, in the store's `pending_meta` table (§3.3), so opening the section on one device clears the dot on every device. One rlx home is one user, so it is the brief's "per-user" marker. It only ever moves forward.
- **`dot_muted`, one per home:** `[pending] dot_muted` in the home's `config.toml`, beside `enabled`, default `false`, written through `pending.settings` (§12.7). It is shared by every device, like the off switch. It is not rlx.app's per-device notification switch.
- **Views, live only:** where the Pending section is open right now. Nothing durable records them, and a view that isn't live counts as closed.
  - **An rlxd connection** (the app; the TUI once it runs on rlxd, handoff §1.9) reports with `pending.view {open}` (§12.8). rlxd holds that state per connection, and a dropped connection is a close.
  - **A TUI that isn't on rlxd** (before handoff §1.9, or with rlxd down) writes `pending_view: true | false` into its own instance record in `<home>/instances/` (`core/instances.py`). It rewrites the record at once when the view changes, not at the next 5 s heartbeat. A record that isn't live (`instances.is_live`) counts as closed.
- **Live clients, for the tray:**
  - `live.tui`: the live records in `<home>/instances/` (`instances.is_live`);
  - `live.app`: rlxd's app-role connections (`status.clients.app`), on any route, local or SSH (DQ-3).

### 12.3 The rule

```text
waiting_unseen = some item has added_seq > last_seen_seq
                 and is still waiting: status "open", or needs_confirm      (DQ-1)
open_anywhere  = some view is open: an rlxd connection, or a live TUI's record
dot            = enabled and not dot_muted and not open_anywhere and waiting_unseen
tray           = dot and live.tui == 0 and live.app == 0
```

- **What moves `last_seen_seq`.** Only these, and only for the person:
  - **a view opens** (`pending.view {open: true}`, or a TUI record turning `pending_view` on). `last_seen_seq` becomes the newest `added_seq`;
  - **an item is added while any view is open.** The computer moves `last_seen_seq` to it at once, so an item added while the section is open sets no dot, either then or after the section closes;
  - **a view closes, or its connection drops.** `last_seen_seq` becomes the newest `added_seq` committed by then: everything that arrived while it was open was on screen;
  - **the tray click** (`pending.seen`, §12.5).
- **What never moves it:**
  - `pending.list`, `pending.get` and `rlx pending list`. The manager reads the list all day, and that must not clear the person's dot;
  - the Claude Code panel;
  - any agent (`not_person`, §12.8).
- **The result, in the brief's words.**
  - An item added while the section is closed sets the dot on every surface.
  - Opening the section on any device clears it everywhere, for good, until the next item arrives while the section is closed.
  - Nothing needs answering to clear it.
- **An item that stops waiting before anyone looks** stops counting (Proposed, DQ-1). Examples: the person answered it in the pane or from the Claude Code panel, or its source resolved it. When no unseen item is still waiting, the dot clears by itself.

### 12.4 Who computes it

- **With rlxd running, the brain computes it.** Its inputs are:
  - the store: the items and `last_seen_seq`;
  - the config: `enabled` and `dot_muted`;
  - rlxd's notifications `view.changed {conn, open}` and `clients.changed {app, tui, remote, cli}`. rlxd sees the app connections;
  - the instances registry, which the brain reads with `core/instances` on every recompute and every 1 s. That gives the TUI's live instances and their `pending_view`.

  It writes each move of `last_seen_seq` with a `pending_log` row (`type: "seen"`), so a write from any process reaches it. It emits `pending.dot_changed` whenever `dot`, `tray` or `muted` changes.
- **With rlxd down,** there is no app.
  - Each TUI computes its sidebar dot with the same function, with `live.app = 0`, and makes the moves of §12.3 for its own view, straight through the pending service.
  - The tray's owner computes `tray` the same way.
- **One function.** `services.pending.dot_state()` is the only code that computes the state, so the brain, a TUI and the tray can't disagree.
- **Ordering.** The brain handles log rows and view changes one at a time, in the order they reach it. When it handles a close, it reads the newest `added_seq` from the store at that moment. So an item committed before the close counts as seen, and one committed after it counts as unseen.

### 12.5 The tray

- **Its owner** is the one tray icon: 0.10.2's Python `rlx service` until task #19, then rlxd as the rlx service (#19). rlx never shows a second icon.
- **It shows the dotted glyph while `tray` is true.** It reads that from `pending.dot_changed` while rlxd runs, and computes it with `dot_state()` while rlxd is down.
- **A click on the dotted icon:**
  1. calls `pending.seen {}`, which clears the dot on every surface at once. It clears at the click even if the surface it opens then fails to start (DQ-6);
  2. opens the Pending section in rlx.app if it is installed, through the app's URL scheme (for example `rlx://pending`; rlxapp names it, HQ-7). Otherwise it opens the TUI at the Pending section: `rlx ui` in the user's terminal, with a flag task #18 adds.
- **"Installed"** means the OS knows the app:
  - macOS: Launch Services resolves `studio.aisquare.rlx`;
  - Windows: the app is registered;
  - Linux: its `.desktop` entry exists.
- **A click on an undotted icon** keeps #19's behaviour: open the app if it is installed, else the TUI.

### 12.6 The OS badge

- While `dot` is true, rlx.app shows a dot: on its macOS dock tile's badge, or as a Windows taskbar overlay icon. It clears it when `dot` turns false.
- It never shows a number, even where the OS offers one, so the badge stays calm.
- The badge exists only while the app runs. The tray covers the time it doesn't (§12.5).

### 12.7 Mute

- **Muting:** `pending.settings {dot_muted: true}`, from the person. On every surface, it is the section's right-click or ⋯ menu, "Mute". Unmuting is the same menu, with `dot_muted: false`.
- **Muted:** `dot` and `tray` are always false. Nothing else changes: the list, the Assumed section, the events and the Claude Code panel all go on as before. The Claude Code panel still lists every item.
- **`last_seen_seq` keeps moving while muted.** Unmuting shows the dot at once if an unseen item is still waiting (Proposed, DQ-5).
- **Mute isn't the off switch.** Off hides the list on every surface (§11). Mute hides only the dot.

### 12.8 Methods and the event

These are added to §6 and §7. Every one returns `pending_off` while the list is off.

- **`pending.view {open}`:** for rlxd connections only (the app; the TUI once it runs on rlxd). The caller must be the person. It records that this connection's Pending section is open or closed, and makes the moves of §12.3.
  - **Result:** `{dot}`, the state below.
  - **Errors:** `not_person`.
- **`pending.seen {through_seq?}`:** moves `last_seen_seq` to `through_seq`, or to the newest `added_seq` by default. It never moves it back. It is for the tray click, and for a surface that holds no view. The caller must be the person.
  - **Result:** `{dot}`.
  - **Errors:** `not_person`, and `invalid_params` for a `through_seq` above the newest.
- **`pending.dot {}`:** reads the state. Any role may call it.
  - **Result:** `{dot}`.
- **The state:** `{dot, tray, muted, last_seen_seq, newest_seq, live: {tui, app}}`. It carries no count of unseen items, because the dot is a dot, not a number. A test can still work one out from the two seqs.
- **`pending.dot_changed`** (topic `pending`): its data is the state, plus `device`, the person's device that cleared or muted it, when one did. It is emitted whenever `dot`, `tray` or `muted` changes. A view opening or closing elsewhere, with no change to them, sends nothing.
- **Settings:** `pending.settings` gains `dot_muted`, and `pending.settings_changed` carries it.
- **The CLI:**
  - `rlx pending dot` (read);
  - `rlx pending seen`;
  - `rlx pending settings --mute-dot` and `--unmute-dot`.

## 13. Versioning, under handoff §7.2

- **No protocol bump.** These are all new, so they keep `protocol_version` 1:
  - the methods: `pending.*`, the dot's `pending.view`, `pending.seen` and `pending.dot` included;
  - the topic `pending`, with `pending.dot_changed`;
  - the fields: `needs_you`'s `pending_id`, and the item's `added_seq`.
- **The capability.** rlxd lists `"pending"` in `hello`'s and `status`'s `capabilities` once it serves the methods. A client checks for it before calling. An older rlxd answers `unknown_method`.
- **Unknown values.** These enums can grow without a bump: `kind`, `source.type`, `answered_by`, `dismissed_by`, `closed_reason`, `delivery.via` and `device.surface`. A client must:
  - show an item whatever its `kind` or `source.type`;
  - decide whether it may answer only from `answer_roles`;
  - treat an unknown `kind` as owner-only when it explains the item.

  The service, not the client, enforces every rule, so an old client can't weaken one.
- **Removing or renaming** a field or an enum value raises `protocol_version` by one, and rlxd serves the previous version for one rlx minor release.
- **Schemas** ship with the implementation, not with this PR, in `rlxd/schemas/v1/`:
  - `pending-item.json`;
  - `pending-event.json` (the eight types);
  - `pending-dot.json` (the dot state of §12.8);
  - `pending-list.json` and the params and results of each method;
  - the CLI's `cli-pending-list.json`, after A1.
- **The store's migration** is Python's own `user_version` step. It is not a protocol version.

## 15. Open questions

Each one is a pick this doc makes provisionally, marked **Proposed** where it appears. None is final until the owner or the hub answers.

### For the owner (the owner rule)

- **OQ-1, authorizations.** Should permission prompts, plan approvals, first-run and trust screens, gate approvals and connector re-auth always be owner-only (§5.1)? **Proposed: yes.** The classifier can't tell a harmless one from a merge, a deletion or a send.
- **OQ-2, what "safe" means.** Should only items classified `preference` or `clarification` ever be assumed (§5.3)? **Proposed: yes.** An unclassified question, an AskUserQuestion in a pane, a blocked task and a failed hand-over then always wait for the person, and an asker opts its question in by classifying it. The alternative is that any unclassified question that isn't owner-only may be assumed, which rests on §5.2's word screen.
- **OQ-3, the manager's own answers.** The brief says the manager "answers items it has found answers to". **Proposed:** the manager may answer any item that isn't owner-only, at any time. Its answer shows in "Assumed: confirm or change", as an assumption does, and a change notifies it. Should manager answers instead be limited to the assumable kinds, or not exist (the manager then replies on the board, and the item closes at its source)?
- **OQ-4, the word screen.** Should §5.2's protected-words screen raise unclassified items to owner-only? **Proposed: yes.** It only ever makes an item wait.
- **OQ-5, how long "Assumed" holds an item.** **Proposed:** until the person confirms or changes it. Should it instead age out, for example after 7 days, counting as confirmed?
- **OQ-6, what "off" stops.** **Proposed:** off stops the sources and hides the surfaces, keeps the items, and the manager carries questions as before. Should off also delete the items?

### For the owner (the unread dot)

- **DQ-1, which items count.** **Proposed:** only unseen items that are still waiting, open or in "Assumed: confirm or change" (§12.3). An item that is answered elsewhere before anyone opens the section stops counting, for example in the pane, from the Claude Code panel, or by its source. With this rule, the dot never points at nothing. The literal reading is that any item added while the section was closed holds the dot until the section opens, even if it has already gone. Which one?
- **DQ-2, the Claude Code panel.** **Proposed:** seeing the panel doesn't count as opening the section, and the panel has no dot (§12.1). It is always on screen, so counting it would keep the dot from ever appearing while a Claude Code session runs. Confirm.
- **DQ-3, who is "live" for the tray.** The design follows the brief's words: any live TUI instance, or any connected app client, keeps the dot off the tray. That includes a TUI reached over SSH (an instance of kind `ssh`) and an app device paired over SSH. But a person sitting at this machine doesn't see those. Should only `native` TUI instances and local-route app connections count, so the tray on this machine still shows the dot? **Proposed:** the brief's words, unless you choose the narrower rule.
- **DQ-4, what "open" means.** The design counts a view as open while the section is on screen anywhere. So a laptop left on the Pending section stops the dot on every other device. Should a view count only while its window is focused or visible, where the surface can tell? Textual reports terminal focus where the terminal supports it, and the app knows its window. Or after some minutes with no input? **Proposed:** the brief's words, "open anywhere", unless you choose one of these.
- **DQ-5, unmuting.** **Proposed:** unmuting shows the dot at once if an unseen item is still waiting (§12.7). The alternative: unmuting marks everything seen.
- **DQ-6, the tray click clears at the click.** **Proposed:** yes, as the brief says, even if the app or the TUI then fails to open (§12.5). The alternative clears only once the opened section reports `pending.view {open: true}`.

### For the hub (security)
