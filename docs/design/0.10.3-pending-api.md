## 0. The design in one screen

- **One list, owned by Python.** Two tables in the rlx store, `pending` (the items) and `pending_log` (every change, in order). Only Python writes them.
- **rlxd serves it and never touches the table.** It forwards every `pending.*` request to the brain (handoff §1.6), with the caller's verified role attached. It publishes the brain's change events on a new topic, `pending`.
- **Every change reaches the stream.** A change and its `pending_log` row commit in one transaction, whichever process makes it: the brain, the CLI, Remote or a hook. The brain tails the log and hands each row to rlxd in order.
- **The owner rule is data, checked by the store.** Every item carries two computed fields, `owner_only` and `assumable`. The store checks them on every manager action, inside the commit itself, whoever calls and through whichever surface.
  - `owner_only` is raised by the asker's flag, the protected kinds, a word screen that runs on every kind, or a question asked again. It is never lowered.
  - Nobody answers or assumes a question they asked or filed: the asker's or the filer's session. That is settled by the hub (OQ-8).
  - Only the person dismisses an owner-only item.
  - Something other than the person resolving it at its source never closes it, and a board note closes only the question it replies to (§4.1).
- **Answering ends in delivering.** An answer commits, and is then delivered to the asker (`delivery.state` follows it). A delivery that fails for good puts the item back on the open list, so a failed delivery never takes a question away. Each source has one deliverer:
  - a board question gets a board note to the asker (Python);
  - a pane dialog gets keys typed into the pane (Python: tmux today, rlxd's PTY host after handoff §1.8);
  - a gate approval becomes `run.decide` (rlxd);
  - a run's question becomes `run.resume {reply}` (rlxd);
  - a connector's re-auth becomes `connectors.login`, then a resume (rlxd, for the app).
- **First answer wins, on every device.** The answer commits by a compare-and-set on the item's `version`, so exactly one answer wins. Every later one gets `already_answered` and delivers nothing, and every device sees the winner in `pending.answered`.
- **Commit, then deliver.** Delivery is a separate step after the commit, made by a delivery worker under a fenced lease, with retries. Every deliverer checks its own source before it acts, so a retry never delivers twice (§9.3).
- **`needs_you` links to pending.** A need that has an answer is a pending item. A need that is only a state (an agent crashed, the manager is down) stays a `needs_you` signal. When both exist, `needs_you.raised` carries the item's `pending_id`, so a client shows one card. There is one list, `pending.list`.
- **The off switch** is one home setting, `[pending] enabled`, on by default. When it is off, every `pending.*` call but `pending.settings` and `pending.poke` returns `pending_off`, the sources stop adding items, and every surface hides.
- **The unread dot** (§12) means "not glanced at yet". The home keeps one `last_seen_seq` and one mute flag, shared by every device.
  - An item added while no surface has the Pending section open sets the dot, on the TUI sidebar and in rlx.app's navigation.
  - When no TUI and no app is live, the tray icon shows it instead.
  - Opening the section anywhere clears it everywhere.
  - Surfaces report an open section with `pending.view {open}`. The brain computes the state and emits `pending.dot_changed`.
- **Open questions are listed in §15.** Every pick on the owner rule or on security is marked **Proposed** and listed there, for the owner or the hub to confirm. None is final.

## 1. Words used here

- **The person:** the human who owns the rlx home.
- **The manager:** the fleet manager agent of the item's project (its board session with role `manager`), or the manager of a parent board the item was routed to.
- **An agent:** any other fleet agent, or any process running inside an agent's pane.
- **An item:** one thing waiting on the person.
- **A source:** what added an item (§4).
- **Delivery:** handing an answer back to the asker (§9).
- **A surface:** where the person sees the list. The brief's three are the Claude Code mod, the TUI and rlx.app. Remote and the CLI also read it.
- **The Pending section:** the list's own place in the TUI and in rlx.app, behind their sidebar or navigation entry. The Claude Code panel is not the section (§12.1).
- **A view:** one surface showing the Pending section right now (§12.2).
- **`pending_seq`:** the durable, per-home sequence number of `pending_log`. It is not rlxd's bus `seq`.

## 2. Where it lives, and who does what

```text
   sources (Python)              rlx store (SQLite, Python only)          rlxd
   board writes ──────────┐      ┌──────────────────────────────┐
   watch-cycle scan ──────┼────▶ │ pending      (items)         │      ┌─────────────────┐
   rlx pending (CLI) ─────┤      │ pending_log  (every change)  │ ◀──▶ │ brain (stdio)   │◀──▶ socket clients
   Remote (needs/answer) ─┘      └──────────────────────────────┘      │  serves pending.*│    app, tui, remote, cli
                                        ▲          tails the log ──────▶│  emits events   │──▶ topic "pending"
   gate and run sources (rlxd) ─────────┘ (as notifications to the brain)└─────────────────┘
```

- **The store** (`core/store.py`) holds `pending` and `pending_log`, added in one migration after the 0.10.2 sync. Their columns are in §3.3.
- **The pending service** (`services/pending.py`) is the only code that writes those tables. It does classification, add, answer, assume, dismiss, confirm and protect. The CLI, the brain, the sources and Remote all call it.
- **The delivery worker** (in the same service) hands committed answers to their askers (§9). It runs in the brain while rlxd runs. With rlxd down, it runs in whichever process committed the answer. A fenced lease (§9.3) lets exactly one worker attempt a delivery at a time, so two workers never deliver twice.
- **The sources** are Python:
  - board sources add their item in the same store transaction as the board event, so a question is on the list the moment it is on the board;
  - pane dialogs, and closing items whose source has resolved, run in the watch cycle. That cycle runs in the brain while rlxd runs, and in `rlx watch` otherwise.
  - The gate and run sources are rlxd's. rlxd hands them to the brain as notifications (§2.1).
- **The brain** (`rlx brain --stdio`, handoff §1.6) serves `pending.*` for rlxd. It tails `pending_log` and hands rlxd one event per row.
- **rlxd** does four things here:
  - it authenticates the caller's role (§8);
  - it forwards requests to the brain;
  - it publishes events;
  - it performs the deliveries only rlxd can make: `run.decide` for a gate item, `run.resume` for a run item, `connectors.login` for a connector's re-auth, and `pty.write` after handoff §1.8.

  It never opens the SQLite file.
- **The CLI, `rlx pending`, and Remote** call the service in their own process (the store path), so they work with rlxd down. Their writes reach rlxd's stream through `pending_log`. When rlxd is up, they also send a best-effort `pending.poke` over the socket (§6.10). The brain then publishes, and starts the delivery, at once rather than on its next tail.

### 2.1 How rlxd reads and writes the list: the brain calls

rlxd and the brain already speak JSON lines over the brain's stdio (handoff §1.6). Pending adds these frames:

```json
{"id": "r41", "method": "pending.answer",
 "params": {"id": "pnd_01m8b2c3d4e5f6g7h8j9k0m1n2", "answer": [{"labels": ["rc/0.10.3"]}], "expected_version": 1,
            "request_id": "8f1c2a"},
 "caller": {"conn": "c12", "role": "app", "client": "rlxapp", "client_version": "0.1.0",
            "verified": "gate", "device": {"name": "anmol-mbp", "route": "local"},
            "origin": null, "peer_agent": null}}
{"id": "r41", "ok": true, "data": {"item": {}}}
{"notify": "pending.event", "pending_seq": 418, "type": "pending.answered", "data": {"item": {}}}
```

- **Requests (rlxd to the brain).**
  - rlxd forwards each socket `pending.*` request as it came, adding `caller`. rlxd fills `caller` from the connection, never from the params:
    - `verified` is `gate` for an app-role connection that passed handoff §5.1's checks, and `token` for every other role;
    - `device` names the paired gate device (task #10) for the app, and is `null` otherwise. For Remote, the Remote server's own device field is passed in the params (§8);
    - `origin` is the client's own `prompt_origin.origin_sender()` (`human` or `agent`), which every rlx client sends in `hello` (§8.2). rlxd passes it on as a claim, and it is `null` for the app;
    - `peer_agent` is set once handoff §1.8 has moved the fleet onto rlxd's PTY host: rlxd then checks whether the socket peer's process descends from a fleet agent's PTY child (§8.2).
  - rlxd returns the brain's envelope under the socket request's `id`.
- **The wait.** The brain replies once the answer has committed, and after waiting up to 10 s for the first delivery attempt (§9.3). rlxd waits up to 15 s, and then answers `brain_unavailable`. That error is retryable. The commit has either happened or not, and a retry with the same `request_id` (§6.3) returns the first call's outcome rather than `already_answered`.
- **Events (the brain to rlxd).** One `pending.event` notification per `pending_log` row, in `pending_seq` order. rlxd publishes each one on topic `pending` with its own bus `seq` and `time` (handoff §7.3), and drops any `pending_seq` it has already published.
  - **After a restart.** rlxd keeps the last `pending_seq` it published in `rlxd.db`. When the brain (re)starts, rlxd sends `pending.resume_from {pending_seq}`, and the brain replays the log rows after it. No change is lost to a restart of either.
- **The tail.** The brain reads new `pending_log` rows every 1 s. It also reads them at once after its own writes, and on a `pending.poke` (§6.10). A write by any process therefore reaches the stream within about a second.
- **The brain asks rlxd to deliver** what rlxd owns (§9). Each of these is a brain-to-rlxd request:
  - `gate.decide_for {conn, run_id, call_id, decision, reason}`. rlxd runs `run.decide` on behalf of connection `conn`, and it checks again, itself, that `conn` is a live app-role connection. So handoff §5.1's "only the app decides" stays enforced in rlxd, not only in the brain. The brain sends it while the app's own `pending.answer` request is still open, so `conn` is the connection that answered;
  - `run.resume_for {run_id, reply, attempt_before}`. Any role may resume a run (handoff §7.5), so rlxd checks no role here. `attempt_before` makes it idempotent: rlxd refuses with `run_alive`, and names the attempt, when the run has already moved past it;
  - `connectors.login_for {conn, id}`, for a connector's re-auth (§9.1). `conn` must be a live app-role connection, because the app opens the sign-in URL and rlx opens none of its own (handoff §5.2, §7.7);
  - `pty.write`, after handoff §1.8, for pane dialogs.
- **Sources (rlxd to the brain).** These are notifications:
  - `source.gate_waiting {pending_id, run_id, call_id, attempt, kind, tool, input, input_sha256, deadline_at, space}`;
  - `source.gate_decided {run_id, call_id, decision, by, device?}`;
  - `source.run_needs_you {pending_id, run_id, attempt, reason, question?, space}`;
  - `source.run_resumed {run_id, attempt}`;
  - `source.runs_erased {run_ids}`;
  - `source.connector_login {login_id, id, status, code?}`, when a login the brain started ends (`connector.login.done` or `connector.login.error`, handoff §7.7);
  - on every brain start, and whenever the list is turned on, two frames (round 3, finding 4):
    - `source.snapshot {gate_waiting: [...], runs_needing_you: [...]}`: what rlxd is waiting on now;
    - `source.outcomes {outcomes: [{pending_id, how, origin, decision?, by?, device?, attempt?}]}`: rlxd's answer to the brain's `source.query {pending_ids}`, which names every open rlxd-sourced item the brain holds.

    rlxd reads each outcome from its durable records (`run.get`'s call ledger and the run's state, handoff §5.4). The `how` is `gate_decided`, `expired`, `run_resumed`, `erased`, or `lost` for an id it no longer knows. The brain applies the §4.1 path to each one. No item is closed for being missing: an owner-only one stays open for the person's confirm, whatever happened while the brain was down or the list was off.

  rlxd mints `pending_id` for its own sources. It can then put the same id in `needs_you.raised` at once (§10), before the brain has written the row.
  - **Only while the list is on.** rlxd keeps the switch's value, from the brain at its start and from every `pending.settings_changed`. While it is off, rlxd mints no `pending_id` and sends no `source.*` notification. Its `needs_you.raised` then carries no `pending_id` (§11).
- **For the unread dot (rlxd to the brain, §12.4),** two more notifications:
  - `view.changed {conn, open, device}` when a connection's `pending.view` changes, or when a connection with an open view drops (`open: false`);
  - `clients.changed {app, tui, remote, cli}` when `status.clients` changes.
- **The brain is down.** `pending.*` calls get `brain_unavailable`. The gate, the runner and `needs_you` keep working: none of them waits on pending.

### 3.2 Every field

The fields the brief names are marked **(brief)**. Every other field says why the API needs it. Times are RFC 3339 UTC with milliseconds, as the bus envelope's `time` is (handoff §7.3).

**Identity and concurrency**
- `id` (string): `pnd_` and a 26-character lowercase ULID. It is stable for the item's whole life. **(brief)**
- `version` (integer ≥ 1): 1 at add, plus 1 on every change. It is what `expected_version` compares against (optimistic concurrency), and clients keep the copy with the highest `version` of each `id` (§7.2). **Added.**
- `added_seq` (integer): the `pending_seq` of the item's `pending.added` row. It never changes. **Added:** the unread dot compares it with the home's `last_seen_seq` (§12.2). It is the brief's "item seq".
- `changed_seq` (integer): the `pending_seq` of the item's last change. It is the durable cursor that `pending.list {since}` filters on. **Added.**

**Who asks, and where**
- `project` (`{id, name}` or `null`) **(brief)**. It is `null` for items with no project: rlx.app runs live in spaces (handoff §2.5).
- `space` (string or `null`): the run's space, for gate and run items. **Added:** an app run has a space and no project.
- `asker` (object) **(brief: "agent label or session")**:
  - `type`: `agent`, `session` (a board session no fleet row holds) or `run`;
  - `label`: what the surfaces show;
  - `role`, `session_id`, `agent_id` and `run_id`: each a string or `null`.

  Delivery uses them to address the answer.
- `filed_by` (`{session_id, role}`, or `null` for rlxd's sources): the board session whose write put the item on the list. It is the asker's own session, or another's that filed it on the asker's behalf: the manager's `rlx pending add`, or the manager that routed a question up. **Added:** the no-self-dealing check (§5.4) refuses the asker's session and the filer's alike. It covers only those two sessions, not every manager of the asker's project, as settled by the hub (OQ-8).
- `fingerprint` (string, 32 hex characters): the SHA-256 of the asker's label, the project id and `text` normalized, cut to 32 characters. Normalized means NFKC, case-folded, whitespace folded to one space, and trailing punctuation dropped. **Added:** a question withdrawn and asked again in the same words is the same question, and keeps its `owner_only` (§5.2). Proposed (OQ-9): it covers only identical normalized text from the same asker, and OQ-9 says what it misses.

**What is asked**
- `kind` (string enum, §5.1): the class of decision. It drives the owner rule. **(brief)**
- `text` (string, at most 8,192 characters): one plain headline. It is what a list row shows. **(brief)**
- `questions` (array, 1 to 8 entries): what the answer flow asks. One entry for every source except a multi-question AskUserQuestion. For one question, `questions[0].text` equals `text`. **Added:** an AskUserQuestion holds up to 4 questions, answered together, so one dialog is one item with several questions. Each question has:
  - `header` (string or `null`): the AskUserQuestion chip, at most 12 characters;
  - `text` (string);
  - `multi_select` (boolean);
  - `free_text` (boolean): whether a typed answer can be delivered to this source. It is true for every source except first-run and trust screens (§4). The brief's "free text always available" holds wherever delivery can carry text;
  - `suggested` (array, 0 to 16 entries) **(brief: "suggested answers, label plus description, the AskUserQuestion shape")**. Each entry is `{label, description, recommended}`, where `label` is a string of at most 200 characters and `description` a string or `null`. `recommended` is true on at most one entry of a single-select question. It marks the suggested default that `pending.assume` takes. An AskUserQuestion option whose label ends in "(Recommended)" reads as `recommended: true`.
- `detail` (object or `null`, at most 16 KiB): what the person must read before answering, by source: the full command of a permission prompt, a plan, or a gate call's `{tool, input, input_sha256, deadline_at}`. It is never pushed to a lock screen (§8.4). **Added:** it is the same split Remote's `NeedsItem` makes between a card's line and what an unlocked page shows.

**The owner rule (§5)**
- `owner_only` (boolean) **(brief)**. Computed at add from the asker's flag, the kind, the word screen and the fingerprint (§5.2). It can be raised later with `pending.protect` (§6.9), and it is never lowered.
- `owner_only_why` (array of `asker`, `protected_kind`, `authorization`, `protected_words`, `reasked` and `raised`): why the item is owner-only. **Added:** a surface can say why an item waits for the person, and a test can assert the reason.
- `assumable` (boolean): whether `pending.assume` can ever take it (§5.3). **Added:** a client can show "waits for you" and the manager need not try.
- `answer_roles` (array of `hello` roles): who may answer the item (§8.3). Gate items and the app-only run items list only `app`. **Added:** a client then needs no knowledge of source types to know whether it may answer.

**Where it came from**
- `source` (object): `{type, key, …}`. Its fields by type are in §4. **Added (the contract's "source ref"):**
  - `key` is unique across all items, open or closed, so a scan that sees the same need again adds nothing (§4.1);
  - the rest is what delivery and closing at the source need.

**Its life**
- `created` (time) **(brief)**.
- `assume_after` (time) **(brief)**: `created` plus `[pending] assume_after_hours` (default 24). It is set on every item. An owner-only item past it stays open (§5).
  - **The floor, Proposed (OQ-7).** An asker may lengthen it, never shorten it: an `assume_after` the asker gives that is earlier than `created` plus `assume_after_hours` is raised to that.
  - **It never moves earlier.** It moves later in one case: turning the list back on gives every open item `max(assume_after, now + assume_after_hours)` (§11). An item frozen while the list was off never becomes assumable the moment it comes back.
- `status`: `open`, `answered`, `assumed` or `dismissed` **(brief)**.
- `answer` (array or `null`) **(brief)**: one entry per question, in order, each `{labels: [string], text: string or null}`. `labels` are suggested labels; `text` is free text. A question needs at least one of the two.
- `answer_text` (string or `null`): one line in words, built by the store, for board notes and list rows. **Added.**
- `answered_by` (enum or `null`) **(brief: person or manager-assumed; extended)**:
  - `person`: the person answered through a surface;
  - `manager-assumed`: the manager took the suggested default after `assume_after` (`status: "assumed"`);
  - `manager`: **added, Proposed (OQ-3).** The manager answered with an answer it found, which the brief's "answers items it has found answers to" asks for. That is allowed only on a `preference` or `clarification` item that isn't owner-only and that the manager didn't ask or file (§5.4). It is kept apart from `person`, so the Assumed section can show it;
  - `elsewhere`: **added.** The source shows the need resolved without pending: a reply on the board to that very question, the dialog gone from the pane, the app's own gate decision, the run resumed, or the task out of `blocked`. Without it, the list would keep a question that had already been answered. It counts as the person only when the resolving write's origin is `human`, and it **never closes an owner-only item, whatever the origin** (round 3, finding 6): only the person's `pending.answer` or `pending.confirm` does. A non-safe kind resolved by an `agent` or `unknown` origin stays open too (§4.1).
- `answered_at` (time or `null`) **(brief)**.
- `answered_device` (object or `null`): `{surface, name, route, client}`, where `surface` is one of `app`, `tui`, `remote`, `cli`, `claude_code` and `manager`. **Added (the contract's "device"):** with several devices, every device shows who answered, from where, as the per-device gate does for decisions (task #10). For the app, `name` is the paired gate device's name and `route` is `local` or `ssh`.
- `delivery` (object or `null`): `{state, at, via, attempts, next_at, ref, detail}`. It is `null` until an answer commits. **Added:** the brief says answering delivers to the asker. Answer and delivery are two steps (§9.3), so this field records how far the delivery has got:
  - `state` is one of:
    - `pending`: committed, not attempted yet;
    - `retrying`: an attempt failed in a way worth retrying, and the next is at `next_at`;
    - `delivered`;
    - `maybe`: a pane write timed out mid-write, so it may have arrived (§9.2);
    - `failed`: the retries ran out, or the failure can't be retried. The item goes back to `open` through `pending.reopened {reason: "delivery_failed"}` (§9.3), so `failed` is never seen on an `answered` or `assumed` item;
    - `superseded`: the source took another answer first, such as the app's policy deciding a gate call. The item then goes through the §4.1 path, never straight to `elsewhere` (round 3, finding 7);
    - `not_needed`: nothing to deliver (a confirm, or a close at the source of an item that had no pending answer). An item whose committed answer was superseded keeps `superseded` instead, whatever its §4.1 outcome, so the record says why the answer didn't land (round 5, point 2);
  - `via` is `board`, `pane`, `gate`, `run`, `connector` or `fleet`;
  - `attempts` is an integer, and `next_at` a time or `null`;
  - `ref` is what was written: `{board, event_seq, woke}` for a board note, `{run_id, call_id, decision}`, `{run_id, attempt}`, `{login_id}` or `{agent_id, keys}`;
  - `detail` is the last attempt's error, `{code, message}`, or `null`.
- `source_resolved` (object or `null`): `{at, origin, how}`, set when the source shows the need resolved or gone without a pending answer. `origin` is `human`, `agent`, `unknown` or `system`; `system` appears only with a gone `how`, which credits nobody (§4.1). `how` is one of:
  - resolved: `board_reply`, `dialog_closed`, `gate_decided`, `run_resumed` or `task_unblocked`;
  - gone: `expired`, `asker_gone`, `erased`, `lost`, `task_dropped`, `switched` or `limit_reset`.

  **Added (C2):** it is how an item that something other than the person closed reaches the person's confirm instead of vanishing (§4.1).
- `needs_confirm` (boolean): true while the person has neither confirmed nor changed one of these. **Added:** it is the brief's "Assumed: confirm or change" section, as one filter:
  - an answer by `manager` or `manager-assumed`;
  - a close at the source, by an `agent` or `unknown` origin, of a `preference` or `clarification` item that isn't owner-only (§4.1). Any other item resolved that way stays open instead.
- `confirmed_at` (time or `null`): when the person confirmed an assumed or manager answer, or a close at the source. **Added.**
- `dismissed_by` (`person`, `asker`, `source` or `null`). **Added:** a dismissal by the person reads differently from an expired gate call.
- `closed_reason` (`resolved_at_source`, `asker_gone`, `expired`, `erased`, `lost`, `task_dropped`, `switched`, `limit_reset` or `null`): set when the source closed the item (`answered_by: "elsewhere"` or `dismissed_by: "source"`). **Added.**

Content is immutable. `kind`, `text`, `questions`, `detail` and `source` never change after add. A dialog whose question changes is a new prompt, with a new `tool_use_id`, so it becomes a new item, and the old one closes at its source. So no client ever answers text other than the text it read.

### 3.3 The store's tables (for task #18)

- **`pending`** has one row per item: every field of §3.2 as a column, or JSON for the objects. It also has:
  - `source_key TEXT NOT NULL UNIQUE`;
  - `answer_request_id TEXT`: the `request_id` of the call whose answer committed (§6.3);
  - `delivery_lease TEXT`, `delivery_fence INTEGER NOT NULL DEFAULT 0` and `delivery_lease_until TEXT`: the delivery worker's fenced lease (§9.3).

  Indexes: `(status, created)`, `(project_id, status)`, `(changed_seq)`, `(added_seq)`, `(fingerprint)` and `(delivery_state, delivery_next_at)`.
- **`pending_log`** has one row per change:
  - `seq INTEGER PRIMARY KEY AUTOINCREMENT`, which is the `pending_seq`;
  - `item_id`, `type` (the event type of §7), `version` and `at`;
  - `actor`: `person`, `manager`, `agent`, `source` or `asker`;
  - `device` (JSON) and `data` (JSON: the event's extras, such as `previous`).

  It is the outbox of §2.1 and the history that `pending.get` returns. A move of the unread dot's marker is a row too (`type: "seen"`, no `item_id`), so any process's move reaches the brain (§12.4).
- **`pending_meta`** is a small key/value table for home-wide state. It holds `last_seen_seq` (§12.2), updated in the same transaction as its `seen` row, and `disabled_at`, when the list last went off (§11).
- **`pending_delivered`** has `key TEXT PRIMARY KEY` (`pending:<id>:v<version>`), with `item_id`, `event_seq` and `at`. A board delivery inserts its row in the same transaction as its note, so a note can be written only once per answer (finding 10).
- **`pending_owner_print`** keeps `(fingerprint, item_id, at)` for every item that was ever owner-only, for 365 days, so asking it again inherits `owner_only` (§5.2) after the item itself is pruned. The period is Proposed (OQ-9).
- **Retention.** A closed item and its log rows are kept for 30 days after closing, as run event logs are (handoff §1.7), then pruned. `seen` rows are pruned after 30 days. An open item is never pruned: "Those wait, however long it takes."

## 4. Sources

### 4.1 The rule every source follows

- **One need, one item, ever.** Each source derives a `source.key` from what the need is about: a board event's seq, a `tool_use_id`, a `call_id`, a run attempt. An add whose key exists is a no-op. So a scan every cycle adds nothing new, and a dismissed item stays dismissed while its source still shows it. A new prompt is a new key, and so a new item.
- **Closing at the source: one path, "the §4.1 path".** Each source also says when its need has gone, and every way an item can leave without a pending answer goes through this one path. That covers:
  - the watch cycle;
  - rlxd's notifications and its snapshot (§2.1);
  - the backfill (§11);
  - a delivery that another answer superseded (§9.1).

  The source records `source_resolved {at, origin, how}`. `how` says what happened, and falls into two groups:
  - **resolved** (someone or something answered): `board_reply`, `dialog_closed`, `gate_decided`, `run_resumed`, `task_unblocked`;
  - **gone** (no answer is possible any more): `expired` (a gate call timed out), `asker_gone` (the agent ended), `erased` (the run was erased), `lost` (rlxd no longer knows the run or call), `task_dropped`, and `switched` and `limit_reset` (a failed hand-over's agent was moved, or its limit reset).

  Then, Proposed (the hub's C2 decisions, rounds 2 and 3; SQ-9):

  | The item | `origin` `human` | `origin` `agent` or `unknown` | `origin` `system` |
  |---|---|---|---|
  | **owner-only, any source, any `how`** | stays `open` | stays `open` | stays `open` |
  | **not owner-only; `kind` `preference` or `clarification`; resolved** | `answered`, `answered_by: "elsewhere"` | `answered`, `answered_by: "elsewhere"`, `needs_confirm: true` | nothing happens |
  | **not owner-only; any other kind; resolved** | `answered`, `answered_by: "elsewhere"` | stays `open` (round 3, finding 3) | nothing happens |
  | **not owner-only; gone** | `dismissed_by: "source"`, `closed_reason` set | the same | the same |

  - **"Stays `open`"** means `source_resolved` is shown with the item, and only the person closes it: their `pending.answer`, their `pending.confirm`, or their `pending.dismiss` (round 3, finding 6). The origin never matters for an owner-only item.
    - A confirm closes a resolved item as `answered_by: "elsewhere"`, and a gone one as `dismissed_by: "source"` with its `closed_reason`.
    - A person's answer to an item whose channel has gone is delivered as a board note to the asker (§9.1).
  - **An owner-only board question never closes on a note,** of any origin (round 2). A note isn't even recorded as its `source_resolved`, so only the person's `pending.answer` or `pending.dismiss` closes it.
  - **`system` never answers.** rlx's own writes (§4.1, below) never resolve an item as anyone's answer. A `system` origin appears only with a gone `how`: rlx's watcher records that the need has ended, which credits nobody.
  - **"Nothing happens"** means the item is unchanged, and no `source_resolved` is recorded.
- **Where `origin` comes from.** There are four values: `human`, `agent`, `system` and `unknown`.
  - **A board reply.** A note resolves a board question only when it replies to it: it carries an explicit `reply_to`, the question's event seq, recorded on the board event (`aisquare note --reply-to <seq>`; task #18 names the flag). A note with no `reply_to` resolves nothing, even one addressed to the asker. So does a note addressed to a role (`--to manager`, `--to coder`), and so does one whose `reply_to` names another question. A note's origin is recorded on the board event at write time:
    - **`system`, by kind, for every write rlx composes:** pending's own deliveries (§9.1), the change note to the manager (§6.3), `fleet tell`'s board fallback (`services/fleet.py`, `tell`), a manager routing a question up (`team._route_up`), and every other note rlx writes for itself. `system` is never `human`, whatever process writes it, and it resolves nothing;
    - **otherwise, the writer's `origin_sender()`:** `human` or `agent` (`core/prompt_origin.py`). This is only "not inside an agent", which is why rlx's own writes are `system` by kind rather than relying on it. A session-less note is no longer taken as the person's (`team.add_note` without `--as`, `remote_needs.py:2180`): its recorded origin decides.

    Recording `reply_to` and the origin is a board change in `services/team.py`, part of task #18.
  - **A dialog gone from a pane:** always `unknown` (finding 2). A dialog answer starts no `UserPromptSubmit`, so no origin marker records who answered it. That covers keys typed by hand at the pane, raw `tmux send-keys`, a Remote quick answer typed outside pending, and an agent's input. An owner-only dialog closed that way stays open for the person, and so does a `question` dialog, the default kind of a pane item. Only a `preference` or `clarification` item goes to "confirm or change" (the table above). The person's own answer through pending is a `pending.answer`, not a close at the source, so it needs no confirm.
  - **The app's own gate decision:** always `unknown` (finding 13). A `run.decide` the app makes directly is its policy's, so it isn't the person's. When the person decides a gate item in rlx.app, the app answers it with `pending.answer` (it renders gate items from the list, §10), and that is a person's answer.
  - **A run resumed, or a task unblocked:** that call's caller origin: `human` or `agent` for a `tui` or `cli` caller, by §8.2. A call rlx makes for itself is `system`, and a call rlx.app makes directly is `unknown` (round 3, finding 10): it is the app's own, policy or UI, as its direct `run.decide` is. The person's reply in the app goes through `pending.answer`.
  - **A failed hand-over that ended** (round 3, finding 9): `how: "switched"` when the agent was moved to another account, by the automatic hand-over or by any `fleet switch`, and `how: "limit_reset"` when its limit reset. Both are `origin: "system"`, rlx's watcher recording that the need has gone, so the item takes the "gone" row of the table above.
  - **rlxd's snapshot and outcomes** (round 3, finding 4): each rlxd-sourced item takes the outcome rlxd reports for it (§2.1). A call the app's policy decided is `gate_decided` with `unknown`; a call that timed out is `expired`; a run resumed by the app is `run_resumed` with `unknown`; an erased run is `erased`; an id rlxd no longer knows is `lost`. A missing item never just vanishes.
- **The off switch.** While `[pending] enabled` is false, no source adds (§11).

## 5. Classification and the owner rule

The owner's rule: assumed answers only for safe, reversible items (preferences, clarifications). The manager never assumes, or answers for the person:
- a merge to main, a release (bump, tag, publish), or spending;
- deleting anything;
- sending a message or email on the person's behalf;
- anything its asker marked owner-only.

Those wait, however long it takes. This section makes that rule a check in the store, run on every manager action, whoever calls.

### 5.1 `kind`

- **The owner's protected kinds:** `merge_main`, `release`, `spend`, `delete` and `send_as_person`. Each is one item of the owner's list.
- **Authorizations, Proposed (OQ-1):** `permission`, `plan`, `first_run`, `gate_call` and `connector_auth`. Answering one lets an agent act, and the classifier cannot bound what that act is: a permission prompt may be `rm -rf` or `gh pr merge`, and a gate call may be a Slack send. So each could be any of the owner's five.
- **Safe classes:** `preference` and `clarification`, the owner's own words.
- **Unclassified:** `question` (the default for a board question and an AskUserQuestion), `blocked` and `handover`.

An asker sets `kind` only on a board question. Every other source sets it by the table in §4.2. A future source must add its kind to one of these four groups, and an unknown kind is treated as an authorization.

**The asker's kind never turns the owner rule off** (C1). A board question filed as `preference` that says "merge to main?" is owner-only through the word screen (§5.2), whatever its kind. The asker's kind can only add protection, by choosing a protected kind, or make an item a candidate for `assumable` (§5.3), which every other check must still allow.

### 5.2 `owner_only`

`owner_only` is true when any of these holds. Each adds its tag to `owner_only_why`:
- **`asker`:** the asker marked the item owner-only;
- **`protected_kind`:** `kind` is one of the owner's protected kinds;
- **`authorization`:** `kind` is an authorization (Proposed, OQ-1);
- **`protected_words`** (Proposed, OQ-4; C1): for **every** kind, the item's text, any question, any suggestion's label or description, or `detail` names a protected act. The words, Proposed (OQ-4, widened in round 2):
  - push, ship, deploy, publish, release, merge, tag, and `main` and `prod` (production) as words;
  - pay, buy, purchase, spend, and credits;
  - delete, remove, drop, and `rm`;
  - send, email, post, and message;
  - a version bump.

  Each word is matched with its forms: `-s`, `-es`, `-ed`, `-d` and `-ing`, plus the irregular sent, paid, bought and shipped. The screen runs on the normalized text (§3.2, `fingerprint`), with word boundaries, so case, spacing and punctuation don't hide a word. It can only raise `owner_only`, never lower it. A false positive makes an item wait for the person, which is the safe direction;
- **`reasked`** (C1; Proposed, OQ-9): an earlier item with the same `fingerprint` (the same asker, project and normalized text) was owner-only (`pending_owner_print`, §3.3). A question withdrawn and asked again in the same words, even under a safe kind, keeps its protection. **What it misses** (finding 4):
  - a reworded question gets a new fingerprint, so it keeps `owner_only` only if the word screen finds a protected word in the new text. One that was owner-only by the asker's flag, by `raised`, or by a protected kind the asker now drops loses it;
  - the same text from another asker is another fingerprint.

  OQ-9 offers alternatives;
- **`raised`:** someone raised it after add, with `pending.protect` (§6.9).

**How `owner_only` is raised, and never lowered** (finding 10):
- **At add,** the store computes it from the five tags above that apply then: `asker`, `protected_kind`, `authorization`, `protected_words` and `reasked`. Content is immutable (§3.2), so the screen never needs to run again.
- **After add,** `pending.protect {id, expected_version?, as?, reason?}` (§6.9) raises it on an item that isn't closed. The person or the item's own asker may call it. It adds `raised`, sets `assumable: false` and adds 1 to `version`, all in one transaction. It emits `pending.updated {change: "protected"}`.
- **A commit in flight loses.** A manager's answer or assume that committed after the raise is impossible, because the commit's own condition requires `owner_only = 0` (§6.3).

Nothing can clear `owner_only`: not the asker, the manager, the person or a later scan. An asker can mark a `preference` owner-only, but it cannot mark a `merge_main` as not owner-only.

### 5.3 `assumable`

`assumable` is true only when all of these hold:
- `owner_only` is false;
- `kind` is `preference` or `clarification`. This is Proposed (OQ-2): the owner's rule names only those. An unclassified `question`, a `blocked` task and a `handover` are never assumed, and an asker that wants its question assumable classifies it;
- every question has a recommended suggestion. For a multi-select question, the recommended entries make the default set.

Two rules act outside any call:

| When | Rule |
|---|---|
| **At add** | an item whose `fingerprint` matches a prior owner-only item is owner-only (`reasked`), whatever kind its asker gives (C1, §5.2) |
| **At the source** | an owner-only item that its source resolved or lost stays open for the person, whatever the origin. Only the person's `pending.answer` or `pending.confirm` closes it, or their dismiss. - **Who calls doesn't matter.** These checks run in the pending service, on the row, for every caller: the CLI, the brain, Remote. They don't rest on rlxd's routing or on what a surface chooses to show.
  - **The commit enforces them.** The commit's compare-and-set (§6.3) carries every owner-rule condition in its own `WHERE` clause:
    - `owner_only = 0` for a manager's answer or assume;
    - `assumable = 1` and `assume_after <= now` for an assume;
    - the caller's session is neither the asker's nor the filer's.

    So a raise or a change that lands between the check and the commit makes the commit fail, rather than slip past it.
- **The order of the checks,** so one refusal always gives the same error: the switch (`pending_off`), the caller (`not_person`, `not_manager`, `not_gate`), `own_item`, the status and version (`already_answered`, `not_open`, `version_conflict`), `owner_only`, `not_assumable` (kind, then no default), and `too_early`.
- **Every refusal is logged.** It writes a `pending_log` row (`type: "refused"`), which `pending.get` shows. It is not an event.
- **Each check is a test.** Task #18's tests drive every row of this table, and a test that can't fail is a bug (handoff, "How to read the checks").

## 6. Methods

Every method is a socket request (`{"id", "method", "params"}`, handoff §7.2). Its result is the v1 envelope. The CLI form is in §6.8. The unread dot's three methods, `pending.view`, `pending.seen` and `pending.dot`, are in §12.8.

Errors every method can return:
- `pending_off`: the switch is off (§11). Every method but `pending.settings` and `pending.poke` (§6.10) returns it;
- `brain_unavailable`: retryable;
- `invalid_params`: `detail` names the field;
- `not_found`: no item has that `id`.

### 6.1 `pending.list {status?, project?, since?, needs_confirm?, limit?}`

- **Params:**
  - `status`: a status, or an array of them. The default is `["open"]`, or every status when `since` is given;
  - `project`: a project id, or `null` for items with no project. Left out, it means every project;
  - `since`: a `pending_seq`. It returns the items with `changed_seq > since`, ordered by `changed_seq`. A client that missed events uses it to re-read only what changed;
  - `needs_confirm: true`: only the "Assumed: confirm or change" section;
  - `limit`: default 200, at most 1,000.
- **Result:** `{enabled, items, counts: {open, open_owner_only, needs_confirm}, pending_seq, more}`.
  - `counts` is over the filter's project, whatever the limit. It is the badge, and the panel's "N more";
  - `pending_seq` is the log head the result reflects;
  - `more` says the limit cut the result. Continue from the last item's `changed_seq`.
- **Order.** Without `since`, the oldest `created` comes first, because everything on the list is waiting and the oldest has waited longest. Surfaces may sort as they like.
- **Errors:** the common ones only.

### 6.2 `pending.get {id}`

- **Result:** `{item, history}`. `history` is `[{pending_seq, at, type, version, actor, device}]`, the item's `pending_log` rows, refusals included.
- **Errors:** `not_found`.

### 6.3 `pending.answer {id, answer, expected_version?, request_id?, as?, device?}`

- **Params:**
  - `answer`: one `{labels, text}` per question, in order (§3.2);
  - `expected_version`: if given and not the item's `version`, the call is refused with `version_conflict` and the current item in `detail.current`. It protects an answer to a card read before the item changed: for example, an assumed item that another device has already changed;
  - `request_id`: a client-chosen string, at most 64 characters. A retry with the same `request_id` returns the first call's outcome, never `already_answered` against itself. Clients send it, so a timed-out call can be retried safely;
  - `as`: the caller's board session, for a manager answer (§8.2);
  - `device`: for Remote and the Claude Code mod only (§8). rlxd ignores it from every other role.
- **What it does, in order** (M4, M6). The answer commits first, and delivery follows it. They are two steps, and only the first is a transaction.
  1. **Check:** the caller, `answer_roles`, the status, `expected_version`, and, for a manager, the owner rule (§5.4). Then that `answer` fits the item. For a pane item, the deliverer also checks once, before anything commits, that the dialog is still up (`stale` otherwise). That keeps an answer to a closed dialog from committing at all. These checks are for clear errors: the commit enforces them again.
  2. **Commit: a fenced compare-and-set.** One `UPDATE … WHERE id = ? AND version = ? AND status = 'open'` (or `AND needs_confirm = 1`, for a change), with every owner-rule condition of §5.4 in the same `WHERE`. It sets:
     - `status`, `answer`, `answer_text`, `answered_by`, `answered_at`, `answered_device` and `answer_request_id`;
     - `delivery = {state: "pending", attempts: 0}`;
     - `version + 1`.

     In the same transaction, it writes the `pending_log` row. That row's `pending_seq` is the commit's sequence, and the event (`pending.answered`, `.assumed` or `.changed`) carries it.
     - **Exactly one caller wins.** When the update touches no row, the caller lost. It re-reads the item and gets `already_answered`, `version_conflict` or the owner-rule error that now applies, and it delivers nothing. No claim, lease or timer decides who wins: the row's `version` does.
  3. **Deliver.** The delivery worker takes the item's fenced delivery lease and makes the first attempt (§9.3). The call waits up to 10 s for that attempt. Its result carries the item with `delivery.state` as it then is: `delivered`, `maybe`, `retrying`, `pending`, `superseded` or `failed`. With `superseded` or `failed`, the item may already be back to `open` (§9.3). On the stream (§9.3), every change of `delivery.state` that leaves the item `answered` or `assumed`, the first attempt's included, is a `pending.updated {change: "delivery"}`. Two cases are excepted:
     - **a move back to `open`** is a `pending.reopened`;
     - **a `superseded` delivery** emits its §4.1 outcome's event: `pending.reopened`, `pending.answered` with `previous`, or `pending.dismissed`. So a device that didn't make the call sees the outcome too (round 5, point 1; round 6).
- **An item in "Assumed: confirm or change".** On an item whose `needs_confirm` is true, a person's answer changes the answer it holds:
  - the status becomes `answered`, with `answered_by: "person"`;
  - the new answer is delivered to the asker. A pane dialog that has gone gets it as a board note to its label instead;
  - the manager gets a board note naming the old answer and the new one ("redo what depended on it"), addressed `--to manager`, which wakes it (`team._addressed_to_manager`);
  - the event is `pending.changed` (§7).
- **An open item that its source resolved or lost without the person** (`status: "open"` with `source_resolved`, §4.1: an owner-only item, or a non-safe kind). A person's answer commits as usual. It is delivered as a board note to the asker, because the original channel has gone, and the manager is told as for a change.
- **Result:** `{item}`.
- **Errors:**
  - `already_answered`: another answer committed first, or the item is closed and isn't a `needs_confirm` item. `detail.item` shows who won and from which device. This is `already_decided`'s counterpart (handoff §5.1);
  - `version_conflict`;
  - `not_person`;
  - `own_item`: the manager asked or filed this item (§5.4);
  - `not_assumable` with `detail.why: "kind"`: the manager answering an item that isn't `preference` or `clarification` (§5.4);
  - `not_gate`: a gate item, or an app-only run item, answered from a role other than `app`. This keeps handoff §5.1's rule;
  - `owner_only`;
  - `bad_answer`. `detail.why` is one of:
    - `label`: a label that is not a suggestion;
    - `count`: the wrong number of answers;
    - `multi`: several labels on a single-select question;
    - `text`: text where `free_text` is false;
    - `empty`;
    - `not_deliverable`: the agent's keys can't express it, §9.2;
  - `stale`: the pane no longer shows that dialog, at step 1. Nothing commits, the item takes its source's close (§4.1), and `detail.current` lists what the pane shows now;
  - `too_late`: the gate call's deadline had already passed at step 1, so nothing commits. The item takes the §4.1 path with `expired`, so, being owner-only, it stays open for the person's confirm. If the deadline passes after the commit, that is a delivery outcome, not this error: the delivery ends `failed` with `detail.code: "too_late"`, and the item comes back through `pending.reopened {reason: "delivery_failed"}` (§9.1; round 5, point 3).

  A delivery that fails after the commit is not an error of this call. It shows in `delivery.state`. A delivery that `failed` after the retries, or one that was `superseded` and that the §4.1 path keeps open, puts the item back on the open list through `pending.reopened` (§9.3).

### 6.4 `pending.dismiss {id, expected_version?, as?, reason?}`

- **Who:** the person. Or the item's own asker, withdrawing its question, but only when the item isn't owner-only (C1). The asker is recognised by `as` naming the asker's session (§8.2). Only the person may dismiss or withdraw an owner-only item.
- **What:** `status: "dismissed"`, `dismissed_by: "person"` or `"asker"`. Nothing is delivered, and the asker is not told: a dismissal says "not now", not "no". `reason` (at most 500 characters) goes into the log. The commit is the same compare-and-set as an answer's (§6.3), with `owner_only = 0` in its `WHERE` when the asker withdraws.
- **Asking again.** A withdrawn question asked again keeps its fingerprint, so it is the same question: if it was ever owner-only, the new item is too (`reasked`, §5.2).
- **Result:** `{item}`.
- **Errors:** `not_open`, `version_conflict`, `not_person`, `owner_only` (the asker withdrawing an owner-only item).

### 6.5 `pending.assume {id, expected_version?, as}`

- **Who:** the manager only (§8.2).
- **What:** it takes each question's recommended suggestion. It commits `status: "assumed"`, `answered_by: "manager-assumed"` and `needs_confirm: true` by §6.3's compare-and-set. The `WHERE` holds `owner_only = 0`, `assumable = 1`, `assume_after <= now`, and the caller is neither the asker nor the filer. The delivery then follows, marked "assumed after N h; the person may change it". It takes no answer of its own: an assumption is always the suggested default.
- **Result:** `{item}`.
- **Errors:** `not_manager`, `own_item`, `not_open`, `version_conflict`, `owner_only`, `not_assumable`, `too_early`.

### 6.6 `pending.confirm {id, expected_version?}`

**Added:** the brief's "confirm or change" needs a confirm.

- **Who:** the person.
- **What:** it sets `confirmed_at` and `needs_confirm: false`. Nothing is delivered.
  - **An item still open with `source_resolved`** (an owner-only one, or a non-safe kind an agent or unknown origin resolved, §4.1): confirming accepts what happened at the source. A resolved `how` closes it as `answered`, `answered_by: "elsewhere"`, `closed_reason: "resolved_at_source"`. A gone `how` closes it as `dismissed_by: "source"`, with `closed_reason` set to that `how`.
- **Result:** `{item}`.
- **Errors:** `not_needed` (the item is neither `needs_confirm` nor resolved at its source), `version_conflict`, `not_person`.

### 6.7 `pending.settings {enabled?, assume_after_hours?, dot_muted?}`

- **Read:** with no params. It returns `{enabled, assume_after_hours, pane_dialog_after_s, dot_muted}`. `dot_muted` is the unread dot's mute (§12.7).
- **Write:** with params, from the person only (`not_person` otherwise). The value is written to `[pending]` in the home's `config.toml` through the CLI's config writer, so config writes stay in the CLI. Then `pending.settings_changed` is emitted.
- **Every other way in is closed too** (finding 6). The config writer refuses every `[pending]` key from an agent origin (`origin_sender() == "agent"`), with `not_person`. That covers `enabled`, `assume_after_hours`, `dot_muted`, `pane_dialog_after_s` and any key added there later. It applies to `rlx config set` (`cli/config.py:52`) and to every other caller of that writer, not only to `pending.settings`.
  - **`rlx config reset`** (`cli/config.py:87`, through `core/config.py:1826`'s `reset_config`) moves the whole file aside, so it would reset every `[pending]` key to its default. From an agent origin, it is refused with `not_person` whenever the file holds a `[pending]` table (round 3, finding 8). A person's reset works as today.
  - **Any later command** that writes or resets config takes the same check. So an agent can't turn the list off, mute the dot or shorten the wait by going round the method.
  - No environment variable overrides a `[pending]` key.
  - A same-user process that edits `config.toml` by hand can't be stopped, as §8.1 says. The brain logs every change to `[pending]` it sees on reload, and emits `pending.settings_changed` with `device: null`, so a change no surface made still shows.
- **The bounds:** `assume_after_hours` is an integer from 1 to 720. A new value applies to items added after it. An item's `assume_after` never moves earlier: it moves later only when the list is turned back on (§11, finding 12).
- **Result** of a read and of a write: `{enabled, assume_after_hours, pane_dialog_after_s, dot_muted}`. After a write, that is the settings as they now stand (tester, #1484).
- **Errors:** `not_person`, `invalid_params`.

### 6.8 The CLI

`rlx pending` maps one-to-one onto these methods, in-process (§2):
- `list` is `pending.list`, and `show <id>` is `pending.get`;
- `answer <id> …` is `pending.answer`;
- `assume <id>` is `pending.assume`. The CLI fills `as` from the agent's own session, as `aisquare` does for `--as`;
- `dismiss <id>` is `pending.dismiss`.

It adds `confirm <id>`, `protect <id>`, `settings [--on | --off] [--assume-after-hours N] [--mute-dot | --unmute-dot]`, `dot` and `seen` (§12.8).

Output:
- `--json` prints the bare `data`;
- `--json --schema-version 1` prints the v1 envelope (handoff §3.1 A1). It waits for #578, like A1's other commands;
- error codes are the API's.

### 6.9 `pending.protect {id, expected_version?, as?, reason?}`

**Added (finding 10):** the way to raise `owner_only` after add.

- **Who:** the person, or the item's own asker, recognised by `as` naming the asker's session (§8.2). Anyone else gets `not_person`.
- **What:** on an item that isn't closed (`open`, or `needs_confirm`), it sets `owner_only: true`, adds `raised` to `owner_only_why`, and sets `assumable: false`. It adds 1 to `version`, writes the item's fingerprint into `pending_owner_print`, and emits `pending.updated {change: "protected"}`, all in one transaction. On an item that is already owner-only, it changes nothing and succeeds.
- **It never lowers.** No method clears `owner_only` (§5.2).
- **Result:** `{item}`.
- **Errors:** `not_open`, `version_conflict`, `not_person`.

### 6.10 `pending.poke {}`

**Added** (tester, #1484, item 1): the store path's nudge to the brain. It is a socket `pending.*` method like the others, and it carries no data.

- **Who sends it:** the CLI, Remote and a TUI on the store path, after every commit they make to `pending_log` or `pending_meta`. That covers an answer, a dismiss, a protect, a settings change, and a `seen` move of the unread dot. A TUI also sends it after it changes its instance record's `pending_view`. It is best-effort: the sender never waits on it, and ignores any error.
- **Who may call it:** any role (`app`, `tui`, `remote`, `cli`) and any actor, agents included (§8.3). It changes nothing and reveals nothing: it only makes the brain look sooner at what the store already holds.
- **What it does:** the brain at once reads the `pending_log` rows after its tail and publishes them (§2.1). It starts the delivery of any newly committed answer (§9.3), and re-reads the instances registry for the unread dot (§12.4). Without a poke, the brain does all of this within about a second anyway.
- **While the list is off:** it is accepted, and never returns `pending_off`. While the list is off, the writes that still happen are settings changes, turning the list back on among them, and their `pending.settings_changed` must reach every surface at once.
- **Params:** none. Any params are ignored.
- **Result:** `{pending_seq}`: the newest `pending_seq` the brain has read.
- **Errors:** `brain_unavailable` only. The sender ignores it.

## 7. Events: topic `pending`

### 7.1 Types and `data`

Every event goes in the handoff §7.3 envelope, with `topic: "pending"`. Every item event's `data` holds `pending_seq` and the whole `item` after the change. Some types add extras, and the two home-wide events (`pending.settings_changed`, `pending.dot_changed`) carry no item:

| Type | When | Extras in `data` |
|---|---|---|
| `pending.added` | a source added an item | none |
| `pending.answered` | an answer was **committed** (§6.3) by the person or the manager, with `delivery.state: "pending"`, or the source resolved the item as answered (`answered_by: "elsewhere"`). That close carries `delivery.state: "not_needed"`, or `"superseded"` when it replaces a pending answer whose delivery lost (§9.3; round 5, point 2). Delivery follows the commit. Its progress arrives as `pending.updated {change: "delivery"}` while the item stays `answered` (`retrying`, `delivered`, `maybe`). A move back to `open` arrives as `pending.reopened`, and a `superseded` delivery as its §4.1 outcome's event (§9.3; tester, #1484, item 2; round 6) | `previous: {answer, answer_text, answered_by, answered_at, answered_device}`, only when the item replaces a superseded answer (§9.1) |
| `pending.assumed` | `pending.assume` committed, with `delivery.state: "pending"`. Its delivery then follows, as an answer's does | none |
| `pending.dismissed` | the person, the asker or the source dismissed it | none |
| `pending.changed` | the person changed an assumed or manager answer, committed with `delivery.state: "pending"`. Its delivery then follows, as an answer's does | `previous: {answer, answer_text, answered_by, answered_at}`, `manager_told: {board, event_seq}` |
| `pending.confirmed` | **added:** the person confirmed one. Other devices drop it from their Assumed section | none |
| `pending.updated` | **added:** an item changed without changing its status. `change` says how: `protected` (§6.9), `rescheduled` (`assume_after` moved, §11), `delivery` (its delivery state moved to `retrying`, `delivered` or `maybe`, leaving it `answered` or `assumed`; §9.3) or `source_resolved` (§4.1) | `change` |
| `pending.reopened` | **added** (tester, #1484, item 3): an `answered` or `assumed` item went back to `open`. Either its delivery failed for good (§9.3), or another answer superseded its delivery and the §4.1 path keeps it open (§9.1). The item comes back with its answer fields cleared and `needs_confirm: false` | `reason: "delivery_failed" \| "superseded"`, and `previous: {answer, answer_text, answered_by, answered_at, answered_device}` |
| `pending.settings_changed` | **added:** the switch, the default or the dot's mute changed. Every surface hides or shows at once | `enabled`, `assume_after_hours`, `dot_muted`, `device`. It has no `item` |
| `pending.dot_changed` | **added:** the unread dot's `dot`, `tray` or `muted` changed (§12.8). Every surface and the tray update together | the dot state, `{dot, tray, muted, last_seen_seq, newest_seq, live: {tui, app}}`, plus `device`. It has no `item` |

### 7.2 How a client keeps the list

1. Read `status` for the bus `seq`, `s`.
2. Subscribe with `events.subscribe {topics: ["pending", …], since: s}`.
3. Call `pending.list`.
4. Apply each event by upserting `data.item` by `id`, keeping the highest `version`. Ordering between the list and the stream doesn't matter, because `version` settles it.
5. On `daemon.gap` (handoff §7.3), call `pending.list {since: <the highest pending_seq seen>}`.

Without rlxd (the Claude Code mod, or the TUI before handoff §1.9), a client polls `rlx --json pending list --since <pending_seq>` instead.

### 7.3 What events carry

- An event carries the item's full text and `detail` to every subscriber that holds the token. That is what the board already gives the same clients. Proposed (SQ-7).
- Remote's push to a lock screen never carries them. It uses a fixed reason passed through `needs_push_safe`, as Remote does today (§8.4).

## 8. Callers, roles and auth

### 8.1 What rlxd can prove, and what it can't

- **The app** (`hello {role: "app"}`) holds a paired, per-device gate credential (task #10). Its answers are the person's, attributed to the gate device's name and route. How strong that is depends on the route (finding 8):
  - **local route:** the credential plus the peer check (handoff §5.1). This is the strongest identity rlx has: `verified: "gate"`;
  - **SSH route:** the credential was minted by a pairing command run inside an authenticated SSH session, and the socket peer is sshd, so no peer check runs. Task #10's open question **q1** applies here: on a macOS host, any same-user process can run that pairing command, and so mint an SSH-route credential with no code-signing check. Until the hub settles q1, an SSH-route app device is only as strong as "a same-user process that ran the pairing command". It is recorded as `route: "ssh"`. **Proposed (SQ-10):** its answers count as the person's, as its gate decisions already do, with the q1 caveat. Its direct gate decisions close a gate item at the source as `origin: "unknown"`, as every app-direct decision does (§4.1).
- **`tui`, `remote` and `cli`** prove only the shared token. Anything that can read the token already runs as the user (handoff §1.3). A same-user process can claim any of those roles.
- **Remote** authenticates its own devices (password, cookie, pairing). The Remote server passes the answering device in `device`, and its pending calls run as the person: role `remote` on the socket, or the store path under `sent_by("human")` (§9.4). rlxd can't check that claim, and treats it as the Remote server's word. A paired Remote device answering owner-only items is Proposed (SQ-2). Today's quick answer (`remote_needs.py:4805`) runs under no `sent_by`, and pending doesn't rely on it: a Remote answer that bypasses pending closes the item at its source as `unknown` (§4.1).
- **The consequence.** No caller identity short of the app's is a security boundary against code running as the user. The owner rule therefore does not rest on caller identity. §5's checks run on the item for every caller, so a forged "manager" can't assume an owner-only item.

  What a forged "person" could do is answer one, and that is the security question for the hub (SQ-1). It is not a new capability, though: an agent that would forge the person's answer to "may I merge to main?" can already run the merge itself. The design blocks the honest-but-wrong paths: a manager answering as the person, or a model relaying an answer. Those are blocked because every rlx process inside an agent is detected as one (§8.2): that covers a model's tool shell, a hook, and a manager that didn't pass `--as`.

### 8.2 Who the caller is: the actor

The service works out an `actor` for every call:
- **`agent`, decided first.** The caller runs inside an agent, by rlx's full detection (M3), which is `core/prompt_origin.origin_sender()` returning `agent`. It reads:
  - a fleet window's `AISQUARE_FLEET_AGENT`;
  - the mark every agent sets in each process it starts, its hooks included (`AgentCapabilities.process_env`: Claude Code's `CLAUDECODE`);
  - any agent's mark of its launch or its tools' shells (`core.spawn.run_agents`: the launch agent, and Codex's `CODEX_THREAD_ID`).

  On the store path, the CLI and Remote call `origin_sender()` themselves. Over the socket, every rlx client sends it in `hello` as `origin`, and rlxd passes it on as `caller.origin` (§2.1). Once handoff §1.8 has landed, rlxd's `peer_agent` also marks a caller whose process descends from an agent's PTY child. That check rlxd makes itself, because it spawned the tree.

  **A caller detected as an agent is never `person`, whatever role it claims.** This holds for every caller but one: the hook path below, whose answer is read from Claude Code's transcript and not taken from the process. A model outside a fleet window still carries `CLAUDECODE`, and a Codex tool shell carries `CODEX_THREAD_ID`, so each is an agent too. A double fork that also clears the environment can still evade detection. §8.1 is why that is acceptable but flagged (SQ-1).
- **`manager`:** a caller detected as an agent whose session is live and holds role `manager` on the item's project board, or on a parent board the item was routed to. The session comes from `as`, or from the agent's own environment, as `aisquare --as` reads it. A manager that passes no `--as` is still an agent, so it is never the person. The CLI fills `as` for it. Before handoff §1.8 this identity is declared, not proven: Proposed (SQ-4).
- **`person`:** a caller not detected as an agent: a connection with role `app`, `tui` or `remote` whose `origin` isn't `agent`; or a `cli` caller whose `origin_sender()` is `human`. Plus the hook path below.
- **The Claude Code mod's hook path** (Proposed, SQ-3). The mod never lets the model write an answer, or choose the words the person reads (finding 5). Its hooks run with `CLAUDECODE` set, so by the rule above they are agents, and the hook path is the one narrow case where the answer still counts as the person's.
  - **Opening.** When the panel opens an answer flow, the mod records the open ask in `run/pending-asks/<session>.json` under the home: the item ids and versions, with at most 4 questions in all, which is AskUserQuestion's limit. The panel pages a longer list. The model is then asked to call AskUserQuestion. Whatever input it composes is never shown as it stands.
  - **PreToolUse rewrites the input.** The mod's PreToolUse hook on AskUserQuestion builds the items' **canonical rendering** from the store, at the recorded versions, and returns it as the tool's input: `hookSpecificOutput.updatedInput`, with `permissionDecision: "ask"`, **never `"allow"`** (round 3, finding 1). With `allow`, Claude Code skips the prompt, and an AskUserQuestion input that already holds answers is how a hook answers it with no person at all. So with `ask`, the person always sees the dialog. The rendering never carries an `answers` field or any pre-selection, only the questions. Each of an item's questions becomes one question, in the recorded order:
    - `header` is `P` and its place, 1 to 4;
    - `question` is the item's question text, as stored, followed by ` [pnd_…]` (the item's id) and, for an item with several questions, `#k`;
    - `options` are that question's `suggested` labels and descriptions, as stored and in order;
    - `multiSelect` is its `multi_select`.

    It records the `tool_use_id` and the rendering's SHA-256 beside the open ask.
  - **When it can't, it denies.** The hook denies the call (`permissionDecision: "deny"`, with a reason the model sees) when there is no open ask for the session, or the rendering can't be built. That covers an item that has changed or closed since the panel opened, and more than 4 questions. An AskUserQuestion that is not about pending items passes untouched, and nothing records it as an answer.
  - **PostToolUse records.** Its PostToolUse hook calls `rlx pending answer --from-hook <tool_use_id>`. The CLI reads two things from the session's own transcript: the `tool_use` input that Claude Code showed, and the `tool_result` holding the person's selections. It answers the items only when all of these hold:
    - the shown input hashes to the recorded rendering;
    - each question names the item's id;
    - each item is still at the recorded version.

    The CLI also refuses any AskUserQuestion input that already holds answers, whether in an `answers` field or as anything a pre-answered input could carry. Even a matching rendering then records nothing.

    Otherwise it records nothing, and the panel says "answer again". The hook's stdin is only cross-checked against the transcript. Each answer carries `actor: person`, `device.surface: "claude_code"` and `expected_version`.

  So a paraphrase can never record the person's answer: the person sees only the stored text, and an answer is taken only against that text. The CLI takes the person actor on this path only for a recorded `tool_use_id`, and once each. A model's own `rlx pending answer` call is an agent's, or the manager's, and is refused or limited as §5.4 says.

  **The mod's first probe** is required before any implementation (round 3, finding 1). It must confirm, in the Claude Code versions rlx supports:
  - that `permissionDecision: "ask"` with `updatedInput` **shows the rewritten questions to the person**, and waits for them;
  - that PreToolUse's `updatedInput` replaces AskUserQuestion's input;
  - that the transcript records both the shown input and the answers;
  - that PostToolUse fires for it.

  **The fallback** if any of them fails: the panel lists items but can't answer them as the person. In a manager session, the model's call counts as a manager answer (`needs_confirm`, and only for the kinds the manager may answer), and in any other session it gets `not_person`.

### 8.4 Text that leaves the machine

Remote's push to a phone's lock screen carries only a fixed reason, passed through `remote_needs.needs_push_safe`. It never carries `text`, `questions` or `detail`, which are served only to an unlocked page. That is today's Remote rule, and pending keeps it.

### 9.2 Pane answers in detail

- **A suggestion** is the agent's key for that option, by index, never by label text.
- **A multi-select question** is the toggle keys, then submit.
- **Free text** is the dialog's type-your-own entry, the text, then Enter. On a permission prompt, free text is "No, and tell Claude what to do differently", then the text.
- **A multi-question AskUserQuestion** answers its tabs in order, then submits once.
- **What the keys can't express** is refused with `bad_answer` and `detail.why: "not_deliverable"`, before anything commits. Each question's `free_text` and `multi_select` already say what the source can take, so a well-behaved surface never sends it.
- **Text checks.** The text passes Remote's `check_remote_text` and its length bound, `SEND_KEYS_TEXT_MAX`.

### 9.3 Commit, then deliver: the worker, its lease and its retries

Answering and delivering are not one transaction (M6). The answer commits first (§6.3), and the worker then delivers it, so typing into a pane or waking an agent always happens outside the commit.

- **The worker.**
  - **With rlxd running,** it runs in the brain. A store-path commit (the CLI, Remote) pokes the brain (`pending.poke`, §6.10), and the brain's tail finds `delivery.state` in `pending` or `retrying` within about a second anyway.
  - **With rlxd down,** the process that committed runs the worker in-process, for the deliveries Python makes: board, task, hand-over and pane. Deliveries only rlxd can make (gate, run, connector) wait in `pending` until rlxd and its brain are up, and then go through. Gate items can't be answered while rlxd is down, because they need an app connection (§8.3). A run question answered then is resumed once rlxd is back: a dead run can be resumed (handoff §5.4).
  - **On start,** a worker picks up every item whose delivery is `pending`, or `retrying` and due, so a crash between commit and delivery never loses an answer.
- **The fenced lease** (M4). Before an attempt, the worker takes the item's delivery lease. That is one conditional `UPDATE`:
  - it sets `delivery_lease = <token>`, `delivery_fence = delivery_fence + 1` and `delivery_lease_until = now + 60 s`;
  - it applies only `WHERE id = ? AND (delivery_lease IS NULL OR delivery_lease_until < now)`.

  It then works under the fence number it read back:
  - **Before the side effect,** it re-reads the row under the fence. It goes ahead only while `delivery_fence` is still its own and at least 20 s of the lease remain. A slow worker whose lease lapsed, and was taken by another, finds a higher fence and stops without acting.
  - **Recording the outcome** is itself conditional on `delivery_fence = <mine>`. A stale worker can't overwrite a newer attempt's outcome.
  - **The lease is released** in that same conditional `UPDATE` (finding 10). It clears `delivery_lease` and `delivery_lease_until` with every outcome: `delivered`, `maybe`, `failed` or `superseded`, and `retrying`, whose next attempt takes a new lease at `next_at`. A worker that dies mid-attempt releases nothing, and its lease lapses after 60 s. The fence never goes down, so the next taker's fence is always higher.
  - **Each deliverer's own check** (§9.1) is the second guard, for a side effect that runs after the fence check. For example, a pane write that lands just as its lease lapses leaves the dialog closed, so the next attempt finds nothing to type.
- **Retries.** A failure worth retrying sets `retrying`, with `next_at`, after 1 s, 5 s, 15 s, 60 s, then 5 min: six attempts in all. After the last one, or on a failure that can't be retried, the delivery is `failed`.
- **A failed delivery puts the item back on the open list** (tester, #1484, item 3). In one transaction:
  - the status moves from `answered` or `assumed` back to `open`;
  - `answer`, `answer_text`, `answered_by`, `answered_at` and `answered_device` are cleared;
  - `needs_confirm` is `false`;
  - `version` gains 1.

  The last answer stays in `delivery.detail`, `{code, message, answer}`. The event is `pending.reopened {reason: "delivery_failed", previous}` (§7.1), and the person sees "not delivered: answer again or dismiss". The item that comes back is a new version, so the next answer is a new compare-and-set, and a stale client gets `version_conflict`.
- **What the caller sees, and every other device** (round 5, point 1; round 6). `pending.answer` returns after the commit and, at most 10 s later, after the first attempt (§6.3). Its result's `delivery.state` is any of `pending`, `retrying`, `delivered`, `maybe`, `superseded` and `failed`. On the stream, one rule covers every change of `delivery.state`, the first attempt's included:
  - **a move back to `open`** (a `failed` delivery, or a `superseded` one that the §4.1 path keeps open) is a `pending.reopened`;
  - **a `superseded` delivery** emits its §4.1 outcome's event: `pending.reopened`, `pending.answered` with `previous`, or `pending.dismissed`, as below;
  - **every other change** (to `retrying`, `delivered` or `maybe`) leaves the item `answered` or `assumed`, and is a `pending.updated {change: "delivery"}`.
- **A superseded delivery** goes through the §4.1 path (§9.1), and its outcome takes that outcome's event:
  - back to `open`: `pending.reopened {reason: "superseded"}`;
  - answered elsewhere: `pending.answered`, with `previous`, and `delivery.state` stays `superseded` (round 5, point 2);
  - gone: `pending.dismissed`, and `delivery.state` stays `superseded` (round 6).

## 10. `needs_you` and pending: linked, one list

**The decision.** Pending links to `needs_you`: it neither supersedes nor wraps it.
- **A need that has an answer is a pending item, and `pending.list` is the one list of them.**
- **A need that is only a state is a `needs_you` signal,** and is never on the list.
- **When both exist they are the same need:** `needs_you.raised` and `needs_you.cleared` carry an optional `pending_id`, an additive field (§13). A client shows that need once, as the pending item.

| Need | `needs_you` (handoff §7.3) | Pending item |
|---|---|---|
| a run's question (`run.needs_you {reason: "question"}`) | `needs_you.raised {source: "run", reason: "question", pending_id}` | yes, `run_needs_you` |
| a run the app stopped (`run.needs_you {reason: "denied"}`) | `needs_you.raised {source: "run", reason: "denied", pending_id}` | yes, app only |
| a connector needing auth (handoff §5.5) | `needs_you.raised {source: "run", reason: "auth", pending_id}` | yes, app only |
| a dialog in a fleet agent's pane (after handoff §1.8) | `needs_you.raised {source: "fleet", reason: <dialog>, pending_id}`, raised by the brain from the same scan, at the moment its item is added: once the dialog has been up for `pane_dialog_after_s` (default 30 s). `needs_you.cleared` comes when the item closes or its source resolves it. With the list off, the same timing applies with no `pending_id` (finding 7) | yes, `pane_dialog` |
| a failed hand-over | `needs_you.raised {source: "fleet", reason: "handover_failed", pending_id}` | yes, `handover_failed` |
| a board question to the person, a task blocked on the person | none: the `board` topic carries the event | yes |
| crashed, lost, manager down, fleet down, a failed turn, interrupted, limited while handing over | `needs_you.raised {source: "fleet", reason}`, with no `pending_id` | no |

- **Why link, and not supersede or wrap.**
  - `needs_you` is in the 0.10.3 contract already. Its checks (handoff §7.3, "needs_you, from runs") and rlxapp's traceability row both rest on it, and its health signals have no answer, so they have no place on a list of questions.
  - Superseding would drop those signals.
  - Wrapping would make the topic a second copy of the list.
  - Linking keeps both contracts as they are, and adds one field. rlxd mints the id for its own sources (§2.1), so the link is present on the first `needs_you.raised`.
- **Remote, the M7 strip and B2's needs-you lane** (0.10.2) follow the same rule once task #18 lands:
  - their decision cards are pending items;
  - their health cards stay;
  - Remote's `POST api/needs/answer` on a card that has a pending item becomes `pending.answer`, so the item closes and every device sees it. Until then, a Remote answer closes the item at its source on the next scan, with origin `unknown` (§4.1): an owner-only item or a non-safe kind stays open for the person, and a `preference` or `clarification` item waits in "confirm or change".
  - The pane source is Remote's own classifier, so the two can't disagree about what is up.
- **rlx.app renders gate items from the list too.** When the person decides one in the app, the app answers it with `pending.answer`, which is the person's answer. A direct `run.decide` is the app's policy, so a gate item it closes reads `origin: "unknown"` (§4.1, finding 13).

## 11. The off switch

- **One value per home:** `[pending] enabled` in the home's `config.toml`, default `true`. It is read by every surface and by the Python sources. It is not rlx.app's per-device notification switch (multi-device brief §4), which stays device-local.
- **Off means:**
  - the sources add nothing;
  - every `pending.*` call but `pending.settings` and `pending.poke` (§6.10) returns `pending_off`, with a hint naming the way back on;
  - every surface hides. The Claude Code mod drops its panel, the TUI drops its panel (M7's strip shows only health), and rlx.app drops its badge, section and cards. Each acts on `pending.settings_changed`, or on a `pending_off` it gets;
  - the manager is told the list is off. Its briefing then asks it to carry questions in its replies, as it did before this feature.
- **Off never touches** the gate, the runner, `needs_you` or the board. A gate call still reaches the app as `run.tool_call`.
- **Items are kept while it is off,** frozen. When it is turned back on:
  - the next watch cycle applies §4.1 to the items whose source has resolved, and adds what is waiting now;
  - **a backfill adds what was asked while it was off** (finding 11). Board sources add only at write time (§2), so a question asked while the list was off has no item. Turning it on runs one backfill, through the normal sources, whose `source.key`s make it a no-op for anything already listed. It reads the board from `disabled_at`, which `pending_meta` records when the list goes off, back at most 30 days, in two steps (round 3, finding 5):
    1. **It lists everything, replies or not:**
       - every board question to the person asked in that window;
       - every task that was blocked on the person in that window;
       - every failed hand-over raised in that window.
    2. **It applies the §4.1 path** to what happened to each one meanwhile:
       - a question's `reply_to` notes, with their origins;
       - a task that has left `blocked`;
       - a hand-over whose agent was switched, or whose limit reset.

       So an owner-only question that someone replied to while the list was off is listed and stays open for the person. A safe one a person replied to closes as `elsewhere`, and one an agent replied to waits in "confirm or change".

    Pane dialogs come with the next scan. rlxd sends a fresh `source.snapshot`, and mints ids for the gate calls and runs still waiting. The brain's `source.query` gets the outcomes of the rlxd items it already held (§2.1);
  - every open item gets a fresh `assume_after = max(assume_after, now + assume_after_hours)` (finding 9), with one `pending.updated {change: "rescheduled"}` each. An item that waited out the off period is never assumable the moment the list comes back.
- **No ids while off** (finding 7). rlxd mints no `pending_id`, and sends no `source.*` notification, while the list is off (§2.1). A `needs_you.raised` then carries no `pending_id`.
- **Only the person can turn it off or on** (§8.3). An agent must not be able to hide the list. This is Proposed (SQ-6).
- **Off also means no dot.** With the list off, `dot` and `tray` are false (§12).

## 12. The unread dot

The owner's addition to the brief, "The unread dot": the dot means "not glanced at yet", not "not addressed". It clears when the person opens the Pending section, whether or not anything has been answered.

### 12.1 Where it shows

- **Shows:**
  - on the Pending entry of the TUI sidebar;
  - on the Pending entry of rlx.app's navigation;
  - on rlx.app's OS badge (the macOS dock, the Windows taskbar), as a dot, never a count (§12.6);
  - on the tray or menu-bar icon, only while neither a TUI nor the app is live (§12.5).
- **Never shows on the Claude Code panel.** The panel always lists the items, muted or not, and has no dot. Seeing the panel doesn't count as opening the section either (DQ-2): the panel is always on screen beside a chat, so counting it would stop the dot from ever appearing while a Claude Code session runs.
- **One state per home.** Every surface shows the same dot, because they all read one state, computed by one function (§12.4).

### 12.2 What is stored, and what is only live

- **`added_seq`, on every item** (a new field in §3.2): the `pending_seq` of the item's `pending.added` row. It is what "the newest item seq" means.
- **`last_seen_seq`, one per home:** the newest `added_seq` the person has seen. It is stored with the list, in the store's `pending_meta` table (§3.3), so opening the section on one device clears the dot on every device. One rlx home is one user, so it is the brief's "per-user" marker. It only ever moves forward.
- **`dot_muted`, one per home:** `[pending] dot_muted` in the home's `config.toml`, beside `enabled`, default `false`, written through `pending.settings` (§12.7). It is shared by every device, like the off switch. It is not rlx.app's per-device notification switch.
- **Views, live only:** where the Pending section is open right now. Nothing durable records them, and a view that isn't live counts as closed.
  - **An rlxd connection** (the app; the TUI once it runs on rlxd, handoff §1.9) reports with `pending.view {open}` (§12.8). rlxd holds that state per connection, and a dropped connection is a close.
  - **A TUI that isn't on rlxd** (before handoff §1.9, or with rlxd down) writes `pending_view: true | false` into its own instance record in `<home>/instances/` (`core/instances.py`). It rewrites the record at once when the view changes, not at the next 5 s heartbeat. A record that isn't live (`instances.is_live`) counts as closed.
  - **An agent-run TUI counts for nothing** (finding 7). Every TUI's instance record also carries `origin`, the TUI's own `origin_sender()` at start. An asq started inside an agent, for example by an agent's `rlx ui`, has `origin: "agent"`. Its `pending_view` is ignored, so it never clears the dot or keeps one from appearing. Over the socket, the same TUI's `pending.view` gets `not_person` (§8.3).
- **Live clients, for the tray:**
  - `live.tui`: the live records in `<home>/instances/` (`instances.is_live`) whose `origin` isn't `agent`. An agent-run TUI never keeps the dot off the tray (finding 7);
  - `live.app`: rlxd's app-role connections (`status.clients.app`), on any route, local or SSH (DQ-3).

### 12.3 The rule

```text
waiting_unseen = some item has added_seq > last_seen_seq
                 and is still waiting: status "open", or needs_confirm      (DQ-1)
open_anywhere  = some view is open: a person's rlxd connection, or a live TUI's
                 record whose origin isn't agent
dot            = enabled and not dot_muted and not open_anywhere and waiting_unseen
tray           = dot and live.tui == 0 and live.app == 0    (live.tui: non-agent TUIs)
```

- **What moves `last_seen_seq`.** Only these, and only for the person:
  - **a view opens** (`pending.view {open: true}`, or a TUI record turning `pending_view` on). `last_seen_seq` becomes the newest `added_seq`;
  - **an item is added while any view is open.** The computer moves `last_seen_seq` to it at once, so an item added while the section is open sets no dot, either then or after the section closes;
  - **a view closes, or its connection drops.** `last_seen_seq` becomes the newest `added_seq` committed by then: everything that arrived while it was open was on screen;
  - **the tray click** (`pending.seen`, §12.5).
- **What never moves it:**
  - `pending.list`, `pending.get` and `rlx pending list`. The manager reads the list all day, and that must not clear the person's dot;
  - the Claude Code panel;
  - any agent (`not_person`, §12.8).
- **The result, in the brief's words.**
  - An item added while the section is closed sets the dot on every surface.
  - Opening the section on any device clears it everywhere, for good, until the next item arrives while the section is closed.
  - Nothing needs answering to clear it.
- **An item that stops waiting before anyone looks** stops counting (Proposed, DQ-1). Examples: the person answered it in the pane or from the Claude Code panel, or its source resolved it. When no unseen item is still waiting, the dot clears by itself.

### 12.4 Who computes it

- **With rlxd running, the brain computes it.** Its inputs are:
  - the store: the items and `last_seen_seq`;
  - the config: `enabled` and `dot_muted`;
  - rlxd's notifications `view.changed {conn, open}` and `clients.changed {app, tui, remote, cli}`. rlxd sees the app connections;
  - the instances registry, which the brain reads with `core/instances` on every recompute and every 1 s. That gives the TUI's live instances and their `pending_view`.

  It writes each move of `last_seen_seq` with a `pending_log` row (`type: "seen"`), so a write from any process reaches it. It emits `pending.dot_changed` whenever `dot`, `tray` or `muted` changes.
- **With rlxd down,** there is no app.
  - Each TUI computes its sidebar dot with the same function, with `live.app = 0`, and makes the moves of §12.3 for its own view, straight through the pending service.
  - The tray's owner computes `tray` the same way.
- **One function.** `services.pending.dot_state()` is the only code that computes the state, so the brain, a TUI and the tray can't disagree.
- **Ordering.** The brain handles log rows and view changes one at a time, in the order they reach it. When it handles a close, it reads the newest `added_seq` from the store at that moment. So an item committed before the close counts as seen, and one committed after it counts as unseen.

### 12.5 The tray

- **Its owner** is the one tray icon: 0.10.2's Python `rlx service` until task #19, then rlxd as the rlx service (#19). rlx never shows a second icon.
- **It shows the dotted glyph while `tray` is true.** It reads that from `pending.dot_changed` while rlxd runs, and computes it with `dot_state()` while rlxd is down.
- **A click on the dotted icon:**
  1. calls `pending.seen {}`, which clears the dot on every surface at once. It clears at the click even if the surface it opens then fails to start (DQ-6);
  2. opens the Pending section in rlx.app if it is installed, through the app's URL scheme (for example `rlx://pending`; rlxapp names it, HQ-7). Otherwise it opens the TUI at the Pending section: `rlx ui` in the user's terminal, with a flag task #18 adds.
- **"Installed"** means the OS knows the app:
  - macOS: Launch Services resolves `studio.aisquare.rlx`;
  - Windows: the app is registered;
  - Linux: its `.desktop` entry exists.
- **A click on an undotted icon** keeps #19's behaviour: open the app if it is installed, else the TUI.

### 12.6 The OS badge

- While `dot` is true, rlx.app shows a dot: on its macOS dock tile's badge, or as a Windows taskbar overlay icon. It clears it when `dot` turns false.
- It never shows a number, even where the OS offers one, so the badge stays calm.
- The badge exists only while the app runs. The tray covers the time it doesn't (§12.5).

### 12.7 Mute

- **Muting:** `pending.settings {dot_muted: true}`, from the person. On every surface, it is the section's right-click or ⋯ menu, "Mute". Unmuting is the same menu, with `dot_muted: false`.
- **Muted:** `dot` and `tray` are always false. Nothing else changes: the list, the Assumed section, the events and the Claude Code panel all go on as before. The Claude Code panel still lists every item.
- **`last_seen_seq` keeps moving while muted.** Unmuting shows the dot at once if an unseen item is still waiting (Proposed, DQ-5).
- **Mute isn't the off switch.** Off hides the list on every surface (§11). Mute hides only the dot.

### 12.8 Methods and the event

These are added to §6 and §7. Every one returns `pending_off` while the list is off, except `pending.poke`, which never does (§6.10).

- **`pending.view {open}`:** for rlxd connections only (the app; the TUI once it runs on rlxd). The caller must be the person. It records that this connection's Pending section is open or closed, and makes the moves of §12.3.
  - **Result:** `{dot}`, the state below.
  - **Errors:** `not_person`.
- **`pending.seen {through_seq?}`:** moves `last_seen_seq` to `through_seq`, or to the newest `added_seq` by default. It never moves it back. It is for the tray click, and for a surface that holds no view. The caller must be the person.
  - **Result:** `{dot}`.
  - **Errors:** `not_person`, and `invalid_params` for a `through_seq` above the newest.
- **`pending.poke {}`** (§6.10): a TUI on the store path sends it after each `seen` move it commits, and after each change to its instance record's `pending_view`, so the brain recomputes the dot at once rather than on its next 1 s read.
- **`pending.dot {}`:** reads the state. Any role may call it.
  - **Result:** `{dot}`.
- **The state:** `{dot, tray, muted, last_seen_seq, newest_seq, live: {tui, app}}`. It carries no count of unseen items, because the dot is a dot, not a number. A test can still work one out from the two seqs.
- **`pending.dot_changed`** (topic `pending`): its data is the state, plus `device`, the person's device that cleared or muted it, when one did. It is emitted whenever `dot`, `tray` or `muted` changes. A view opening or closing elsewhere, with no change to them, sends nothing.
- **Settings:** `pending.settings` gains `dot_muted`, and `pending.settings_changed` carries it.
- **The CLI:**
  - `rlx pending dot` (read);
  - `rlx pending seen`;
  - `rlx pending settings --mute-dot` and `--unmute-dot`.

## 13. Versioning, under handoff §7.2

- **No protocol bump.** These are all new, so they keep `protocol_version` 1:
  - the methods: `pending.*`, including `pending.protect` and the dot's `pending.view`, `pending.seen` and `pending.dot`;
  - the topic `pending`, with `pending.updated`, `pending.reopened` and `pending.dot_changed`;
  - the fields:
    - `needs_you`'s `pending_id`;
    - `hello`'s `origin` (§8.2);
    - the item's `added_seq`, `filed_by`, `fingerprint` and `source_resolved`;
    - `pending.answer`'s `request_id`;
  - the error code `own_item`.
- **The capability.** rlxd lists `"pending"` in `hello`'s and `status`'s `capabilities` once it serves the methods. A client checks for it before calling. An older rlxd answers `unknown_method`.
- **Unknown values.** These enums can grow without a bump: `kind`, `source.type`, `answered_by`, `dismissed_by`, `closed_reason`, `owner_only_why`, `delivery.state`, `delivery.via`, `source_resolved.how`, `pending.updated`'s `change`, `pending.reopened`'s `reason`, and `device.surface`. A client must:
  - show an item whatever its `kind` or `source.type`;
  - decide whether it may answer only from `answer_roles`;
  - treat an unknown `kind` as owner-only when it explains the item.

  The service, not the client, enforces every rule, so an old client can't weaken one.
- **Removing or renaming** a field or an enum value raises `protocol_version` by one, and rlxd serves the previous version for one rlx minor release.
- **Schemas** ship with the implementation, not with this PR, in `rlxd/schemas/v1/`:
  - `pending-item.json`;
  - `pending-event.json` (the ten types);
  - `pending-dot.json` (the dot state of §12.8);
  - `pending-list.json` and the params and results of each method;
  - the CLI's `cli-pending-list.json`, after A1.
- **The store's migration** is Python's own `user_version` step. It is not a protocol version.

| nits | `pending.dismiss` and `pending.protect` take `as`. §5.2 and §6.9 give `pending.protect` the same params. A `pending.settings` write returns the settings as they now stand |
| round 5: `pending_off` | with the list off, every `pending.*` method but `pending.settings` and `pending.poke` exits 1 with `pending_off`, the dot's three included. `pending.poke` exits 0. §14's off-switch row and this table's row 1 both pass on one home |
| round 5, points 1 to 4 | a first attempt that delivers gives a `pending.updated {change: "delivery"}` with `delivered`, as well as the call's result. A superseded answer closed `elsewhere` keeps `delivery.state == "superseded"`, not `not_needed`. A gate answer whose deadline passes after the commit gives `pending.reopened {reason: "delivery_failed"}`, with `delivery.detail.code == "too_late"`. A superseded gate answer's result item is already `status == "open"` |

## 15. Open questions

Each one is a pick this doc makes provisionally, marked **Proposed** where it appears. None is final until the owner or the hub answers.

### For the owner (the owner rule)

- **OQ-1, authorizations.** Should permission prompts, plan approvals, first-run and trust screens, gate approvals and connector re-auth always be owner-only (§5.1)? **Proposed: yes.** The classifier can't tell a harmless one from a merge, a deletion or a send.
- **OQ-2, what "safe" means.** Should only items classified `preference` or `clarification` ever be assumed (§5.3)? **Proposed: yes.** An unclassified question, an AskUserQuestion in a pane, a blocked task and a failed hand-over then always wait for the person, and an asker opts its question in by classifying it. The alternative is that any unclassified question that isn't owner-only may be assumed, which rests on §5.2's word screen.
- **OQ-3, the manager's own answers.** The brief says the manager "answers items it has found answers to". **Proposed (the hub's round-2 decision, awaiting the owner):** the manager may answer only `preference` and `clarification` items that aren't owner-only and that it didn't ask or file, at any time. Its answer shows in "Assumed: confirm or change", as an assumption does, and a change notifies it. Everything else waits for the person, or for an assume after `assume_after` (safe kinds only). The word list alone isn't trusted: "Push the fix to main?" filed as a `question` is refused by kind, even before the words catch it. Should manager answers exist at all, or should the manager only reply on the board?
- **OQ-4, the word screen.** §5.2's protected-words screen raises items to owner-only. It runs on every kind, so the asker's own kind can't switch it off. The round-2 list adds push, ship, deploy, main, prod and the other forms (§5.2). **Proposed (the hub's C1 and round-2 decisions, awaiting the owner): yes.** It only ever makes an item wait. Confirm the word list, and whether it should grow further, for example with "go live", "rollout" and "invoice".
- **OQ-5, how long "Assumed" holds an item.** **Proposed:** until the person confirms or changes it. Should it instead age out, for example after 7 days, counting as confirmed?
- **OQ-6, what "off" stops.** **Proposed:** off stops the sources and hides the surfaces, keeps the items, and the manager carries questions as before. When the list is back on, open items get a fresh `assume_after` (§11). Should off also delete the items?
- **OQ-7, the floor on `assume_after`.** **Proposed:** an asker may only lengthen an item's wait, never shorten it below the home's `assume_after_hours` (§3.2). Only the person sets that, from 1 h to 720 h. Is the home's setting the right floor, or should there be a fixed minimum, such as 24 h, that the person can't lower either?
- **OQ-9, asking again** (the hub's C1 decision). **Proposed:** an item inherits `owner_only` when an owner-only item with the same fingerprint (the same asker, project and normalized text) existed in the last 365 days (§3.3). **Its real limits** (finding 4):
  - only the identical normalized text inherits;
  - **a reword keeps `owner_only` only for an item that was owner-only by `protected_words`,** because the word screen sees the protected word again in the new text. An item that was owner-only by the asker's flag, by `raised`, by a protected kind the asker drops, or by `authorization` loses it when it is reworded and asked again under a safe kind;
  - **it doesn't cross askers:** the same text from another asker is a new fingerprint.

  **Alternatives**, which could be combined:
  - **(a) sticky per asker and project.** Once an asker has an owner-only item in a project, every item it asks there for the next N hours (say 24) is owner-only too;
  - **(b) per project, not per asker.** Drop the asker from the fingerprint, so another asker's identical text inherits too;
  - **(c) un-flag by the person only.** Under (a) or (b), only the person can lower an inherited `owner_only`, with a new `pending.unprotect`. That is the one exception to "never lowered", and it is the person's alone.

  Which, if any?

### For the owner (the unread dot)

- **DQ-1, which items count.** **Proposed:** only unseen items that are still waiting, open or in "Assumed: confirm or change" (§12.3). An item that is answered elsewhere before anyone opens the section stops counting, for example in the pane, from the Claude Code panel, or by its source. With this rule, the dot never points at nothing. The literal reading is that any item added while the section was closed holds the dot until the section opens, even if it has already gone. Which one?
- **DQ-2, the Claude Code panel.** **Proposed:** seeing the panel doesn't count as opening the section, and the panel has no dot (§12.1). It is always on screen, so counting it would keep the dot from ever appearing while a Claude Code session runs. Confirm.
- **DQ-3, who is "live" for the tray.** The design follows the brief's words: any live TUI instance, or any connected app client, keeps the dot off the tray. That includes a TUI reached over SSH (an instance of kind `ssh`) and an app device paired over SSH. But a person sitting at this machine doesn't see those. Should only `native` TUI instances and local-route app connections count, so the tray on this machine still shows the dot? **Proposed:** the brief's words, unless you choose the narrower rule.
- **DQ-4, what "open" means.** The design counts a view as open while the section is on screen anywhere. So a laptop left on the Pending section stops the dot on every other device. Should a view count only while its window is focused or visible, where the surface can tell? Textual reports terminal focus where the terminal supports it, and the app knows its window. Or after some minutes with no input? **Proposed:** the brief's words, "open anywhere", unless you choose one of these.
- **DQ-5, unmuting.** **Proposed:** unmuting shows the dot at once if an unseen item is still waiting (§12.7). The alternative: unmuting marks everything seen.
- **DQ-6, the tray click clears at the click.** **Proposed:** yes, as the brief says, even if the app or the TUI then fails to open (§12.5). The alternative clears only once the opened section reports `pending.view {open: true}`.

The probe that `ask` really shows the rewritten questions is required before implementation;
  - the CLI refusing any input that already holds answers;

  - one use of each.
