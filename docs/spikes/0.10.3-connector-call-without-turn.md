# Spike: one connector read call, and tool listing, without a model turn (ask H)

Task #5 (`tsk_01m8a1wmng83bwebqq4k79fmt6`), 2026-11-25. This spike has no product code. It
answers board note #585 (b) and (c), the Engine spec §5 (WatchJob), and handoff §2.4, §5.3 and
§5.5.

- **Claude Code:** `2.1.332 (Claude Code)`, the native build at `~/.local/share/claude/versions/2.1.332`.
- **Host:** macOS (Darwin 27.2.0, arm64).
- **Account:** one rlx account slot, signed in with claude.ai. It has two claude.ai connectors:
  `claude.ai Claude Docs` (9 tools) and `claude.ai TickTick` (59 tools). rlxapp's E6 used another
  account, with Slack and Gmail. Both accounts reach their connectors through the same
  `claudeai-proxy` transport (see route d).

## Verdict

**Yes on both counts, through one route:** the `stream-json` control channel of a plain
`claude -p` process.

- **Calling a tool.** The `mcp_call` control request runs one MCP tool through Claude Code's own
  MCP client, including claude.ai connectors, without a model turn.
- **Listing tools.** The `mcp_status` control request lists every connector with its status and
  its tools. Each tool carries `annotations.readOnly` and `annotations.destructive`.
- **No user message.** Neither request needs one, so no turn can start.
- **The gate decides the call.** With `check_permissions: true`, plus
  `--permission-prompts host --permission-prompt-tool stdio`, the call reaches the host as a
  `can_use_tool` request with the exact input:
  - the host's deny means the tool never runs;
  - its allow runs exactly one call.

**What rlxd needs:**
- **No new binary.** It needs only `claude` itself, at a version whose `initialize` response
  lists `mcp_call_check_permissions_v1`.
- **No credential of its own.** It uses Claude Code's existing login, through the
  `CLAUDE_CONFIG_DIR` / `CLAUDE_SECURESTORAGE_CONFIG_DIR` pass-through (handoff §4.3). rlxd reads
  no Keychain item.
- **Three upstream asks:**
  - make `mcp_call` and `mcp_status` documented, stable SDK surface;
  - report `readOnlyHint` as tri-state;
  - document `--permission-prompt-tool stdio`.

  See "What rlxd would need".

## How the probes were run

**Environment.** Each probe started one `claude` process, the way rlxd would:
- **Clean environment:** `env -i HOME USER LOGNAME PATH TMPDIR LANG CLAUDE_CONFIG_DIR`, where
  `CLAUDE_CONFIG_DIR` is the account slot's own config dir. There was no temporary config dir,
  and no setting, login or connector was changed.
- **An empty working directory**, in the session scratchpad.
- **Stdin held open** until the last reply. E9 showed that connectors load only while stdin is
  open.
- **A disposable harness** drove the process: a Python script, not committed, kept in the session
  scratchpad. It:
  - wrote the JSON lines below to stdin;
  - answered `can_use_tool` with `allow` or `deny`;
  - logged only shapes: event types and subtypes, reply keys, server names and status, tool names
    and annotations, and content block types and lengths.

  No tool output text was recorded, and server IDs are redacted below as `mcpsrv_<id>`.

**Base command**, with flags added per probe as noted:

```sh
claude -p --input-format stream-json --output-format stream-json --verbose \
  --tools "" --no-session-persistence --setting-sources project \
  --debug-file <scratch>/<probe>.debug.log
```

- **P1 and P2** add `--permission-mode dontAsk --permission-prompts none`.
- **P3** adds `--permission-mode manual --permission-prompts host`.
- **P4 to P7** add `--permission-mode manual --permission-prompts host --permission-prompt-tool stdio`.
- **P6** also adds `--strict-mcp-config`.

**Every probe starts with** `{"type":"control_request","request_id":"init1","request":{"subtype":"initialize"}}`.
Every `initialize` reply lists, under `capabilities`: `mcp_call_check_permissions_v1`,
`mcp_call_result_not_for_model_v1` and `mcp_call_soft_error_result_v1`.

**How "no model turn" is measured.** Three signals, all required:
1. No `assistant` event.
2. No `result` event: no `num_turns` and no `usage` at all, since a `result` comes only after a
   turn.
3. No model request in the debug log: no `[API REQUEST] /v1/messages` line and no
   `Stream started` line.

**The control run, P6.** It sent one user message on purpose and shows all three signals firing:
- one `assistant` event;
- `result/success` with `num_turns: 1`, and usage of 2 input, 2494 cache-creation, 649 cache-read
  and 4 output tokens;
- `[API REQUEST] /v1/messages … source=sdk` in its debug log.

So the detector does fire on a real turn, and the zeros elsewhere are real zeros.

**The read call.** `mcp__claude_ai_TickTick__get_tool_details` with `{"tool_name":"list_tags"}`.
- The server marks it `readOnly: true` (P1).
- It returns the documentation of another tool and no user data.
- No write, send, create, update or delete tool was called.

## Route a: the `mcp_call` control request: works

**Where it comes from.** Claude Code 2.1.332 defines a `control_request` subtype `mcp_call`. Its
schema text, read from the installed binary, says:
- "Invokes an MCP tool via the subprocess MCP client without a model turn."
- "No permission check (control channel is trusted, same as other subtypes) unless
  check_permissions is set."
- "A target server that is not yet connected is brought up on demand: … waits up to 30s … for
  the server to connect".

**Its fields:**
- `tool` takes the fully-qualified name.
- `arguments` takes the input.
- `check_permissions`, when true, decides the call "as the model's own call to this tool is":
  rules, mode, hooks, and `can_use_tool` to the host. It also says: "Only a CLI that says
  mcp_call_check_permissions_v1 honours this member: an older one ignores it and runs the tool
  with no check."
- `result_not_for_model` asks for the server's own content blocks, unprocessed. It is honoured
  only on the spawning host's own pipes.
- `soft_error_result` asks for the tool's own `isError` result.
- `timeout_ms` / `expires_at` route the call through a staging engine. Not used here.

A web search of the public Agent SDK docs found no documentation of `mcp_call`, so treat it as
undocumented (ask 1 below).

### P2: one ungated call
- **Stdin after `initialize`:**
  `{"type":"control_request","request_id":"call1","request":{"subtype":"mcp_call","tool":"mcp__claude_ai_TickTick__get_tool_details","arguments":{"tool_name":"list_tags"},"result_not_for_model":true}}`,
  then EOF.
- **Result: works.**
  - Exit 0, 4.38 s.
  - Events: `control_response/success` (initialize, 0.17 s), then `control_response/success`
    (call1, 3.03 s).
  - The reply's keys are `content`, `structuredContent` and `_meta`. `content` is one `text`
    block (3384 characters of JSON), and `isError` is absent.
  - 0 `assistant` events, 0 `result` events, 0 `/v1/messages`.
  - The debug log has exactly one `Calling MCP tool: get_tool_details`, completed in 398 ms.
- **Connecting on demand.** The call was sent before the connector had connected (P7 shows
  TickTick connects about 2.7 s after start). Claude Code waited for it.
- **Note.** This ran under `--permission-mode dontAsk --permission-prompts none`, and the call
  still ran: **without `check_permissions`, `mcp_call` bypasses every permission check.**

### P3: gated, but without `--permission-prompt-tool stdio`
- **Stdin:** P2's request with `"check_permissions":true` added.
- **Flags:** `--permission-mode manual --permission-prompts host`.
- **Result: refused, and the host was never asked.**
  - Exit 0.
  - Events: `system/permission_denied` (2.38 s), then `control_response/error`: "The tool did not
    run: Claude requested permissions to use mcp__claude_ai_TickTick__get_tool_details, but you
    haven't granted it yet."
  - 0 `can_use_tool` requests, 0 `Calling MCP tool`.
- **Takeaway.** Fail-closed, but the gate gets no say. `--permission-prompts host` alone does not
  make the stdin host the prompt handler: the SDK's hidden `--permission-prompt-tool stdio` flag
  does.

### P4-deny and P4-allow: gated through the host
- **Stdin:** as P3.
- **Flags:** add `--permission-prompt-tool stdio`.
- **The `can_use_tool` request the host receives** (P4-deny, 2.61 s):

  ```json
  {"type":"control_request","request_id":"…","request":{"subtype":"can_use_tool",
   "tool_name":"mcp__claude_ai_TickTick__get_tool_details",
   "input":{"tool_name":"list_tags"},
   "mcp_server":{"name":"claude.ai TickTick","source":"claudeai"},
   "display_name":"Get Tool Details","tool_use_id":"toolu_mcp_call_<hex>",
   "server_policy_ask_only":false,"suppress_always_allow_rule":true}}
  ```

  - `input` is exactly the request's `arguments`, so the gate can check `input_sha256`.
  - The `toolu_mcp_call_` prefix marks a control-channel call, as distinct from a model's call.
- **Deny.** The host answered
  `{"type":"control_response","response":{"subtype":"success","request_id":"…","response":{"behavior":"deny","message":"spike: denied by host"}}}`.
  - The reply was `control_response/error`: "The tool did not run: spike: denied by host".
  - 0 `Calling MCP tool`, 0 turns. Exit 0, 4.05 s.
- **Allow.** The host answered `{"behavior":"allow","updatedInput":{"tool_name":"list_tags"}}`.
  - Events: `can_use_tool` (2.28 s), then `control_response/success` (2.84 s), with the same
    content shape as P2.
  - Exactly one `Calling MCP tool`; 0 `assistant`, 0 `result`, 0 `/v1/messages`. Exit 0, 4.32 s.

## Route b: a pre-built `tool_use` turn, or a resume trick: fails

- **P5.** After `initialize` and a 4 s wait, stdin got an `assistant` message holding one
  `tool_use` block for the same tool and input. Then 10 s of wait, then EOF.
- **What happened:**
  - Claude Code's stdin reader accepts `type: "assistant"` lines: the parser passes them through.
  - Nothing ran: 0 `can_use_tool`, 0 `Calling MCP tool`, 0 `assistant` or `result` events, 0
    `/v1/messages`. Exit 0, 15.54 s.
  - So a pre-built assistant turn does not execute its tool.
- **The resume trick was not probed.** It needs a hand-crafted session file in the account's
  `projects/` dir, which is a write into Claude Code's data. Route a already gives a gated call
  with no turn. And a resume that runs the tool and then continues is a model turn by
  definition.

## Route c: `claude mcp serve`: fails

- **What was run.** `claude mcp serve` over stdio, with the same clean environment and empty
  directory. JSON-RPC `initialize`, `notifications/initialized`, an 8 s wait, then `tools/list`.
- **Result.** Exit 0. 26 tools: `Agent`, `Bash`, `Read`, `Edit`, `Write`, … `ToolSearch`.
  - None is an `mcp__*` or connector tool.
  - None carries annotations.
- **Takeaway.** It serves Claude Code's own built-in tools, not the connectors it mounts.

## Route d: MCP straight to the connector endpoint: stopped at the credential

From the P1 debug log, with IDs redacted:
- **The connector list.** Claude Code fetches it from
  `https://api.anthropic.com/v1/mcp_servers?limit=1000&include_additional_installs=true`.
- **The connections.** It connects each claude.ai connector through the `claudeai-proxy`
  transport at `https://mcp-proxy.anthropic.com/v1/mcp/mcpsrv_<id>`. `mcp_status`'s `config`
  shows `{"type":"claudeai-proxy","url":"<the connector's own URL>","id":"mcpsrv_<id>"}`.
- **The credential.**
  - The binary's transport code throws `No claude.ai OAuth token found` without the claude.ai
    OAuth token.
  - On macOS, Claude Code reads that token with
    `security find-generic-password -a "<user>" -w -s "<service>"`. The service name ends in
    `-credentials` and is keyed by the config dir (`CLAUDE_SECURESTORAGE_CONFIG_DIR`).

So route d would need rlxd to read, and refresh, the user's claude.ai OAuth token out of the
Keychain. Handoff §4.3 forbids that: rlx's `/usr/bin/security` is the only Keychain reader, and
rlxd links no Keychain library. **Stopped there:** no request was sent to the proxy, and no
Keychain item was read.

## Route e: listing with `readOnlyHint` and no model turn

### e1, `mcp_status`: works (P1, P7)
- **Stdin:** `{"type":"control_request","request_id":"st8","request":{"subtype":"mcp_status"}}`.
- **The reply.** `{"mcpServers":[…]}`, one row per server, with these keys: `name`, `status`,
  `scope`, `source` (`claudeai`), `transport` (`claudeai-proxy`), `config`, `serverInfo`,
  `sessionProxied` and `tools`.
- **Each tool** is `{name, annotations, _meta?}`. `annotations` may hold `readOnly`,
  `destructive` and `openWorld`.
- **P1**, exit 0, 9.77 s, three `control_response` events and nothing else:
  - At 0.4 s: `mcpServers: []`.
  - At 8.4 s, `claude.ai Claude Docs` is `connected` with 9 tools:
    - `readOnly: true` on `read`, `query`, `guide` and `export`;
    - `destructive: true` on `delete`;
    - `{}` on the other 4.
  - At 8.4 s, `claude.ai TickTick` is `connected` with 59 tools:
    - 29 have `readOnly: true`;
    - 5 have `destructive: true` (the `delete_*` tools);
    - 25 have only `openWorld: true` (the `create_*`, `update_*` and similar tools).
  - 0 `assistant`, 0 `result`, 0 `/v1/messages`. The only other hosts in the debug log are
    `v1/mcp_servers`, `mcp-proxy` and telemetry.
- **Caveats for rlxd:**
  - **The hint is two-state, not three.** The binary builds `readOnly: v.isReadOnly({}) || void 0`
    and `destructive` the same way. So a tool whose server says `readOnlyHint: false` and a tool
    with no hint both come back as `{}`.
    - rlxd can give `read_only_hint: true` or `null`, never `false`.
    - The gate treats not-true as a write anyway (rlxapp §4), so this is safe, but 5.3's
      `true | false | null` can't be met as written (ask 2).
  - **Tool names are the server's own** (`get_tool_details`), not fully qualified. rlxd builds
    `mcp__<server name, non-[A-Za-z0-9_-] → _>__<tool>`; P6's error names the server
    `claude_ai_TickTick`.
  - **Early `[]`.** Up to about 0.5 s after start, before the claude.ai list is fetched,
    `mcpServers` is `[]`. So an early `[]` means "not fetched yet", not "absent".

### e2, `system/init`: partial
- **It needs a turn.** With no user message, no `system/init` was emitted in P1, P2, P4, P5 or
  P7. In P6 it came 0.02 s after the user message, so reading it costs a turn.
- **No annotations.** Its schema has `tools: string[]` (names only, as E6 saw), and
  `mcp_servers` with name and status.

### e3, `claude mcp list` / `claude mcp get "claude.ai TickTick"`: partial
- **Both exit 0.**
- **`list`** prints `claude.ai Claude Docs: https://api.anthropic.com/v1/pages/mcp - ✔ Connected`
  and `claude.ai TickTick: https://mcp.ticktick.com - ✔ Connected`.
- **`get`** prints `Scope: claude.ai config` and `Status: ✔ Connected`.
- **Neither** shows tools or annotations, and neither has a `--json` flag.

## #585 (c), re-confirmed: `--tools "" --strict-mcp-config` mounts nothing (P6)

- **Flags:** the P4 flags plus `--strict-mcp-config`.
- **Stdin:** `initialize`, an 8 s wait, `mcp_status`, then the gated `mcp_call` from P4, then one
  user message ("Reply with the single word OK. Do not call any tools."). This is the spike's
  only model turn.
- **Results.** Exit 0, 17.06 s.
  - `mcp_status` (8.18 s): `mcpServers: []`.
  - `mcp_call` (13.2 s): `control_response/error` "MCP server not connected: claude_ai_TickTick".
    There was no `can_use_tool` and no `Calling MCP tool`; it waited about 5 s, then failed.
  - `system/init` (13.22 s): `mcp_servers: []`, `tools: []` (0 tools, 0 `mcp__` tools).
  - Then `assistant`, `rate_limit_event` and `result/success` with `num_turns: 1`. This is the
    control run used above.
- **Takeaway.** E11 holds on 2.1.332. Also, a tool-less process can't reach a connector even
  through `mcp_call`.

## §5.5 (ask J): connector states are visible before the first message (P7)

- **What was run.** `mcp_status` polled every 0.25 s for about 4 s, with no user message. Exit 0;
  0 `assistant`, 0 `result`.
- **States over time:**

  | Time | Claude Docs | TickTick |
  |---|---|---|
  | 0.16 s and 0.41 s | — (`[]`) | — (`[]`) |
  | 0.66 s | `pending` | `pending` |
  | 1.18 s | `connected` (9 tools) | `pending` |
  | 2.72 s | `connected` | `connected` (59 tools) |

- **Takeaway.** §5.5's Route 1 (`connectors.gate_before_turn`) is open: rlxd can poll
  `mcp_status` until every named connector is `connected` before it sends the first message.
  Treat `[]` before the list fetch as `pending`, not `absent`.

## What rlxd would need

**1. A run shape for `connectors.call`, no user message ever.** This is a suggestion; §5.3 owns
the contract.
- Spawn `claude` with the P4 flags in an empty directory, keeping stdin open.
- Send `initialize`.
- Refuse with `no_route` unless the reply's `capabilities` lists
  `mcp_call_check_permissions_v1`. An older CLI ignores `check_permissions` and runs the call
  unchecked.
- Send exactly one `mcp_call` with `tool`, `arguments` = the pinned input,
  `check_permissions: true` and `result_not_for_model: true`, plus `soft_error_result: true` if
  the app wants the tool's own `isError`.
- Route the `can_use_tool` request to the gate. The gate checks `tool_name` against the pin and
  `sha256(RFC 8785(input))` against `input_sha256`. On allow, rlxd answers with
  `updatedInput` equal to the pinned input, so the decision can't change the call.
- Return the `control_response`'s `content` / `structuredContent` raw to `match`.
- Close stdin. `num_turns: 0` holds by construction: no `user` line is ever written.
- **Never send `mcp_call` without `check_permissions`.** That path skips every permission check
  (P2).
- **Timing.** About 3–4 s per call on a cold process, mostly the connector's connect. A watch
  could keep one process per account warm, but each fire is still one `mcp_call`.

**2. `connectors.list {refresh: true}` with no turn.** Same spawn and `initialize`, then poll
`mcp_status` until no named connector is `pending` (or a timeout), then close. This earns
`connectors.no_turn`. Map `annotations.readOnly == true` to `read_only_hint: true`, and anything
else to `null`.

**3. Binary and credential.**
- **The binary:** only `claude`, found on the `PATH` from §4.3. This spike used 2.1.332; the
  earliest version with `mcp_call_check_permissions_v1` is unknown, so feature-detect, don't
  version-pin.
- **The credential:** none of rlxd's own. Claude Code reads its login itself, and rlxd only
  passes `CLAUDE_CONFIG_DIR` / `CLAUDE_SECURESTORAGE_CONFIG_DIR` through (§4.3).

**4. Upstream asks**, to Claude Code:
- **Ask 1.** Document `mcp_call` (with `check_permissions`) and `mcp_status` as supported,
  versioned Agent SDK control requests. Today they exist only in the CLI's schema text, and no
  public doc covering them was found.
- **Ask 2.** Have `mcp_status` report each tool's raw MCP hints (`readOnlyHint`,
  `destructiveHint`, `openWorldHint`), with `false` kept apart from "absent".
- **Ask 3.** Document `--permission-prompt-tool stdio` (hidden today), or make
  `--permission-prompts host` route `mcp_call` asks to the stdin host by itself (P3).

**Side effects of the probes.**
- Each `claude` start rewrites the slot's `.claude.json`. That is Claude Code's own bookkeeping,
  the same as any run.
- One telemetry batch per process.
- No setting, login, connector or session file was changed (`--no-session-persistence`
  throughout).
- **Connector tool calls that reached a server: 2**, both to `get_tool_details`, a read-only tool
  (P2 and P4-allow).
- **Attempts refused before any server was reached: 3** (P3, P4-deny and P6).
